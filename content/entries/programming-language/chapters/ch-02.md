# 第二章 命令式与声明式

语言在「怎么描述计算」上，有最根本的两条路线：**命令式**与**声明式**。差别不在语法漂亮与否，而在你写给机器的是「一步步怎么做」还是「我要什么、你帮我求」。这条分野贯穿几乎所有语言的设计，理解它，才能看懂为何有的语言适合系统、有的适合数据。本章把两条路线摆正，并看它们如何混合。

## 命令式：告诉机器每一步

**命令式**语言模拟「图灵机」的直觉：程序是一串改变状态的指令。你说「把 x 设为 0，然后循环每个元素，若大于 x 就把 x 更新为它」——这是在描述**步骤**与**状态变化**。绝大多数日常语言（如系统级语言、脚本语言）默认是命令式。它的好处是直观、贴合硬件、易于预测执行顺序；缺点是状态到处可变，程序一大，就很难说清「此刻某变量到底是什么」，错误随之藏于隐式的相互影响中。

## 声明式：告诉机器要什么

**声明式**语言反其道：你描述「目标是什么」，把「怎么达成」交给系统去求。数据库查询语言是典型——你写「选出工资高于平均的员工」，并不写「先算平均、再遍历比较、把符合的收集起来」，后者由查询引擎自己决定最优做法。声明式的魅力是让人聚焦意图、系统负责效率；代价是你对执行细节的控制变弱，遇到性能诡异时更难插手。它适合「描述约束、求解满足约束的结果」这类问题。

> 📝 编者注：命令式与声明式不是「低级与高级」的代名词。声明式未必更高级，只是在特定问题（查询、配置、规则）上更贴合。硬拿声明式写底层设备管理，反而别扭。范式选错，代码会比用错工具还难受。

## 函数式：无状态的近亲

声明式家族里，**函数式**最重要。它的信条是「避免可变状态与副作用」：计算靠函数从输入映射到输出，同样输入永远同样输出，不偷偷改外部。这带来可推理性——你不必追踪全局状态，就能断定一段代码的行为；也天然利于并行，因为无共享可变状态就少竞争。纯函数式语言把这点推到极致，主流语言则折中：允许函数式写法、保留可变状态以备性能。函数式是命令式在「状态管理」上的反思，也是并发时代被重新看重的原因。

## 混合与务实

现实里多数语言是多范式：主体命令式，却内嵌声明式与函数式特性。你可用循环（命令式），也可写查询式表达（声明式），还可把逻辑抽成无副作用函数（函数式）。这种混合让程序员按子问题的性格挑最顺手的那部分，而不必为范式 purity 牺牲实用。语言设计的成熟，往往体现在「把对立范式调和进一身」——既给控制的力，又给抽象的静。第二章看清「怎么描述」；第三章进入另一维度——类型系统，看语言如何用「标注意义」在出错前拦住一类错误。

## 面向对象：封装状态的另一路范式

在命令式与声明式之外，**面向对象**是另一股塑造现代语言的力量，尤其适合「用状态描述世界」的问题。它的核心是把「数据」与「能操作这些数据的行为」捆成一个**对象**，对外只暴露接口、藏起内部状态，这叫封装——你不必知道一个银行账户对象内部怎么存余额，只需调用「存款」「取款」，正确性交由对象自己维护。对象间通过「方法调用」协作，复杂系统便由许多各管一段的对象拼成，职责清晰、便于团队分工。配合**继承**与**多态**，可让「更一般的类」派生出「更具体的类」，复用共性、各添个性，调用方却能统一对待不同子类。面向对象的兴起，正是因为它把「命令式易乱的状态」装进了有边界的盒子，让大程序不再是一盘散沙。它当然也常被误用——过度继承会织出脆弱的层级、为复用而复用反增耦合，所以现代语言与社区也提倡「组合优于继承」。理解面向对象，是看懂绝大多数二十世纪后期至今主流语言及其设计争论的一把钥匙。值得注意的是，面向对象并非命令式的对立面，而是一种「如何组织状态」的强化：它底层仍是一步步改状态，只是把状态锁进了对象内部、用方法作为唯一入口。也正因如此，它与函数式「消灭可变状态」的信条天然张力，当代许多语言于是同时提供两套工具，让程序员在「要封装协作」时取向对象、在「要纯推理并行」时取函数式，范式之争最终常化为同一门语言里的风格选择。
