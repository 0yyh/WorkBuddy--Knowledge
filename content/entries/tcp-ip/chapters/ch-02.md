## IP 与 TCP：寻址路由 + 可靠传输

TCP/IP 的两大基石是 **IP**（网际层）与 **TCP**（传输层）。一个只管「送到」，一个负责「送好」；把这两件事分开，是整个架构能同时容忍异构网络与苛刻应用的关键。

### IP：无连接、尽力而为

**IP**（RFC 791，IPv4；RFC 8200，IPv6）是网际层的核心。它是**无连接、尽力而为**的协议：每个分组独立携带源与目的 IP 地址，各自经不同路径抵达，网络不保证顺序、不保证一定送达、也不保证不重复。

IP 首部中的**生存时间（TTL）**每经一个路由器减一，减到零即丢弃，以防分组在网络中无限循环；**分片与重组**则处理链路的最大传输单元（MTU）限制——当分组大于某段链路可承载的大小时，IP 把它切小，到目的主机再拼回，从而让异构网络可以无缝接力。IPv4 还有首部校验和、服务类型与选项字段；IPv6 则简化了首部、取消了路由器分片，并把地址扩展到 128 位。地址空间的分层与聚合（无类别域间路由）保证了全球路由表可管理，而地址转换（NAT）在 IPv4 地址耗尽后以地址复用的方式延长了它的寿命。正是这种「不假设底层」的极简设计，使 IP 能跨越以太网、卫星、无线等任何介质。

### TCP：在不可靠之上建可靠

**TCP**（RFC 9293，2022 年整合并取代 RFC 793）在 IP 之上提供**可靠字节流**：

- **三次握手**建立连接：`SYN` → `SYN+ACK` → `ACK`，双方确认收发能力并同步初始序列号；关闭时再以四次挥手优雅释放。
- 用**序列号与确认号**保证有序与完整：接收方对已收到的连续字节给出累积确认，发送方为每个未确认的段设置**重传超时**，超时未确认即重传。
- **滑动窗口**做流量控制：接收方通过窗口字段声明还能接收多少字节，防止快发送方淹没慢接收方。
- **拥塞控制**探测网络容量：慢启动从一个小段起指数增长，达到阈值后转为拥塞避免的线性增长，丢包时按算法降窗。经典实现包括 Tahoe、Reno 与 NewReno，现代则有 CUBIC 以及基于带宽时延积建模的 BBR。拥塞控制既关键又易失灵——它是整条网络「礼貌」的基石，却在无线链路与长肥管道上遭遇挑战。

TCP 因而成为网页、邮件、文件传输等「不容许出错」业务的首选。

### UDP 与 QUIC：另一类取舍

并非所有流量都需要 TCP 的开销。**UDP**（RFC 768）省去连接建立与重传机制，首部只有 8 字节，适合实时音视频、在线游戏、域名查询——偶尔丢包比延迟更可接受。

**QUIC** 则在 UDP 之上重新实现可靠传输与安全（内置 TLS 1.3），并以独立的多条流避免队头阻塞，支持 0-RTT 重连与连接迁移，成为 HTTP/3 的底座。它代表了近十年传输层最重要的思路转变：**与其改造中间设备难以升级的 TCP，不如在用户态、在 UDP 之上从头实现一套可演进的传输协议**。

### 「连接」到底是什么

TCP 的连接并非物理线路，而是双方共同维护的一段状态，它由**四元组**唯一标识：源 IP、源端口、目的 IP、目的端口。因此同一台主机的同一个服务端口可以被多个客户端同时连接而互不混淆——端口解决的正是「同一主机上多个进程复用一条链路」的问题，这也是传输层之所以必要的原因。连接的状态体现在序列号与窗口的同步上：建立时协商初始序列号，传输中通过确认号相互推进。这也解释了为什么长时间静默或中途丢包会让连接失效，以及为什么服务器重启会使既有连接瞬间作废。

### 可靠与高效之间的取舍

TCP 把「不丢、不乱、不重」的责任全揽在自己身上，代价是延迟：一次丢包需要等待重传定时器或快速重传，期间后续数据被压在缓冲区；遇到高丢包或长时延链路，吞吐会明显下滑。这正是实时业务偏爱 UDP 的原因——它们宁可丢一帧，也不愿整体卡住。QUIC 则试图两者兼得：保留可靠交付与拥塞控制，同时让每条流的交付不受其他流影响，并把握手与加密合并以减少往返。**传输层的演进，本质上是在「可靠性、时延、公平性」三者之间不断重新分配预算。**

> 📝 编者注：IP 与 TCP 的分工里藏着一条朴素原则——**网络只该做一件事：尽力把分组送到；其余的智能，留给两端的主机**。把可靠性与拥塞控制这类需要端到端信息的功能放在传输层，而不是中间的路由器上，才有了今天既能承载电话与视频、又能承载文件与页面的同一张网络。
