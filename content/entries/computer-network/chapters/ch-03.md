# 第三章 传输层——TCP与UDP

IP 层只管「把包送到某台机器」，却不关心机器里哪个程序该收、也不保证包不丢不乱。这件事交给**传输层**。它用「端口号」指明目标进程，并在不可靠的 IP 之上，按应用需要叠出「可靠」或「轻快」两种性格。代表就是 TCP 与 UDP，一个像挂号信，一个像广播喊话。

## 端口：主机内的门牌

一台机器同时跑网页、邮件、视频，IP 只能把包送到机器，是谁的得靠**端口号**——一个十六位的编号，像大楼里的房间号。网页常用八十、邮件各有约定。传输层头部带上源端口与目标端口，接收方据此把数据交给正确的程序。端口加 IP 构成「套接字」地址，唯一标定一次通信的两端。没有端口，多任务的主机便无法区分该把数据给谁。

## TCP：用确认换可靠

**TCP（传输控制协议）**的目标是「像本地读写一样可靠」。它先三次握手建立连接，给每个字节编序号；接收方收到后回送确认，发送方超时未收到确认便重传；接收方还按序号重组、丢弃重复、补漏掉的，保证数据完整、有序、不重。它为防网络被单一洪流冲垮，内置**拥塞控制**：探测可用带宽、丢包就减速，像文明司机踩油门也知让路。可靠是有代价的：握手、确认、重传带来延迟与开销，实时性受限。

> 📝 编者注：TCP 的「可靠」指数据不丢不错不乱达，并不指「快速」或「必达应用层语义正确」。它保证字节流完整，却不保证你的程序用得对。把 TCP 当成「包治延迟」是常见误解。

## UDP：轻装上前线

**UDP（用户数据报协议）**反其道而行：无连接、不发确认、不重传、不排序，发完就忘。它头部极简、延迟极低，适合容忍少量丢失却不容忍延迟的场景——语音通话漏一句可补，卡半秒却难受；直播、游戏、域名查询都偏爱它。应用若需可靠，可自己在 UDP 上加一层（如某些视频与游戏协议）。UDP 把「可靠性取舍」交还给应用，体现了网络设计的哲学：底层提供最小可用原语，复杂策略按需叠加。

## 两兄弟如何分工

选 TCP 还是 UDP，看应用对「可靠」与「及时」的偏好。文件传输、网页、邮件要一字不差，选 TCP；实时音视频、在线对战要低延迟、能丢帧，选 UDP。两者并非对立，而是同一传输层上针对两种需求的两种实现。值得注意，现代还有在 UDP 上自建可靠与安全的协议（如 HTTP 的新传输层），说明边界在流动。传输层解决了「端到端交给谁、交得稳不稳」；第四章上到应用层，看 DNS 与 HTTP 这类我们每天真正用到的协议，如何在这套地基上盖起万维网。

## 可靠之外的智慧：流量控制与拥塞避免

TCP 的可靠靠序号与重传，但光有重传还不够，否则发送方一股脑猛发，会把接收方缓存冲爆、也会把中间网络挤垮。它因此另有两套机制。**流量控制**解决「别把接收方淹了」：接收方在每次确认里告诉发送方「我还能收多少」（窗口大小），发送方据此收住油门，这叫滑动窗口，它保护的是接收端这台具体机器。**拥塞控制**则解决「别把网络挤垮」：发送方维护一个随网络状况伸缩的拥塞窗口，起初慢启动、指数探路，发现丢包就减速，通畅再缓升；两套窗口取较小者决定真正发送量，于是既照顾接收方肚量、又顾及网络脾气。拥塞控制在八十年代后期才加入 TCP，此前一次轻微丢包就可能引发「所有主机同时重发、网络更堵、再重发」的雪崩，史称拥塞崩溃。这段历史说明，可靠协议不仅要对端对得好，还要对全网有责任心——TCP 的克制，是互联网规模化的隐形功臣，当年互联网能从几十台主机长到几十亿设备，这份自觉功不可没。现代拥塞控制已演化出多个流派，有的追求高吞吐、有的偏好低延迟；它们共享「探测—响应」的基本逻辑，却在对「丢包意味什么」的判断上各有哲学，而新的控制算法也不再单纯依赖丢包、转而观察延迟变化。TCP 在可靠与效率之间的反复权衡，至今仍是网络研究里最活跃的议题之一。对普通用户而言，这些机制最直接的体现，就是「网页在弱网下也不会瞬间崩掉，而是缓缓变慢」——那正是 TCP 在默默踩刹车、为全网让出余地。理解它，能让人对偶发的卡顿多一分体谅，也对底层协议设计的精巧多一分敬意。
