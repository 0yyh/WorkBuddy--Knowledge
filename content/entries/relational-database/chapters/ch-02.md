## SQL 与声明式查询

**SQL（Structured Query Language）** 是关系数据库事实上的标准语言，国际标准编号 **ISO/IEC 9075**。它最初由 IBM 在 System R 项目中以 SEQUEL 之名开发，用于验证关系模型的工程可行性。

### 声明式：只说要什么

SQL 的核心特征是**声明式**：你写「我想要哪些满足条件的数据」，而不写「先扫哪张表、用什么索引、怎么连接」。把「取数路径」交给**查询优化器**，是关系模型数据独立性的直接延伸——同一句 SQL，优化器会根据表大小、索引与统计信息选择不同的**执行计划**（顺序扫描、索引扫描、哈希连接、嵌套循环、排序合并等），并在代价模型下选出估算成本最低的一个。

这也是 SQL 的微妙之处：写得一样的语句，在不同数据分布下可能跑出完全不同的性能；而「让优化器选对路」正是索引设计、统计信息维护与查询重写的工作目标。

### 查询骨架

一条典型查询由子句组合：

- `SELECT` 投影要返回的列，可含聚合函数（`COUNT`/`SUM`/`AVG`/`MIN`/`MAX`）；
- `FROM` 指定来源表与连接方式；
- `WHERE` 在分组前筛选行；
- `GROUP BY` / `HAVING` 分组与分组后过滤；
- `ORDER BY` 排序，`LIMIT`/`OFFSET` 分页。

其**逻辑执行顺序**常与书写顺序不同：先 `FROM` 与 `JOIN` 形成中间关系，再 `WHERE` 过滤，然后 `GROUP BY` 聚合、`HAVING` 过滤组，接着 `SELECT` 计算输出列，最后 `ORDER BY` 排序。`JOIN` 按匹配键把多张表合并成一张结果表，并区分内连接（只保留匹配行）与外连接（`LEFT`/`RIGHT`/`FULL`，保留不匹配行并补空值），使「跨整个关系模式」的查询能写成单个表达式——这是关系模型对真实业务（订单连客户、成绩连课程）最直接的价值。

### 一句查询要走过的几道关

把执行路径完整走一遍，就明白声明式的力量与代价各在哪里。SQL 文本先经**词法与语法分析**变成语法树，再由**语义分析**校验表名、列名与类型；随后**重写**阶段做恒等式化简与视图展开；**优化器**枚举可能的连接顺序与存取路径，用统计信息估算每步的输出行数并计算代价，选出计划；**执行器**按计划取数、连接、聚合与排序，最后把结果编码返回。这条链路上每一环都可能出错或失准：统计信息过期会让优化器误判，参数变化会让同一个计划由优转劣，复杂连接的计算量又可能随表数呈组合式膨胀。**「写得清楚、建得合理、必要时看计划」，因此是 SQL 调优的三件事。**

### 标准的演进

SQL 自 1986 年首个国际标准 **SQL-86** 起，经 **SQL-92**（广为人知的大版本）、**SQL:1999**（引入递归查询、触发器、窗口函数、XML）、**SQL:2003**（XML 与 OLAP）、**SQL:2016**（JSON、多态表）、**SQL:2023**（增强 JSON 与环类型）多次演进。绝大多数主流数据库（PostgreSQL、MySQL、Oracle、SQL Server）都「近似实现」该标准，并各自扩展出方言。

因此 SQL 是**工程近似，而非关系模型的严格化身**：它允许 `NULL` 与三值逻辑（真、假、未知，影响过滤与聚合的结果），允许重复行，也不保证结果顺序——这些都与科德理想化的关系相去甚远。

### NULL 与三值逻辑的陷阱

`NULL` 表示「未知」，这让 SQL 的比较变成**三值逻辑**：`NULL = NULL` 的结果不是真，而是未知；`NULL` 与任何值做算术仍是 `NULL`。由此产生两类常见困惑：`WHERE 列 <> 5` 会漏掉该列为 `NULL` 的行，必须显式补上 `IS NULL`；聚合函数（`COUNT(*)` 除外）会跳过 `NULL`，导致平均值与直觉不符。`NULL` 的存在还使唯一约束、连接与分组的行为都带上例外条款。它提醒我们：**现实数据里「缺失」与「为零」是两件事，而 SQL 用一个记号同时承担了两者。**

### 视图、索引与查询重写

声明式的收益要靠配套机制兑现。**视图**保存的是查询而非结果，可用来隔离表结构变化、简化复杂查询，物化视图则把结果落盘换取查询速度；**索引**（B 树、哈希、位图、全文、部分索引）为优化器提供可选的存取路径，代价是写入变慢与空间占用；**查询重写**（谓词下推、连接消除、子查询解嵌套）在语义等价的前提下把计划改得更好。三者共同构成「同一句 SQL、不同的执行计划」这一调优空间——**这也说明声明式并不等于放弃控制，只是把控制从「怎么写」搬到了「怎么建」。**

### 从 SQL 到 NoSQL 再回到 SQL

2000 年代，Web 规模扩张催生了一批「不用 SQL」的系统：键值库、文档库、宽列库与图库，它们以放弃连接与强一致换取横向扩展。但十多年后出现了明显的回流——多数系统补上了类 SQL 查询语言、二级索引与事务支持，NewSQL 更直接把事务带进分布式环境。原因不难理解：**业务的查询需求总会复杂化，而声明式查询与事务语义是最难在应用层重建的两样东西。** SQL 的胜出，一半来自标准，一半来自它承载了四十年积累的优化器与运维经验。
