## 请求/响应模型与报文

HTTP 的本质是一次「一问一答」：**客户端发请求，服务器回响应**。这套问答有固定的语法与语义，而 RFC 9110 把语义从具体版本中抽离出来，使之成为所有 HTTP 版本共享的核心。

### 请求的四个部分

一个 HTTP 请求由四部分构成：

- **方法（method）**：表达操作意图。最常见的 `GET` 用于获取资源，`POST` 用于提交数据；另有 `PUT`（整体替换）、`DELETE`、`HEAD`（只取首部）、`OPTIONS`（询问支持能力）、`PATCH`（局部修改）等。方法是**幂等性**讨论的核心：`GET`/`PUT`/`DELETE`/`HEAD` 被定义为幂等，重复执行与执行一次的效果相同；`POST` 不幂等，重发可能造成重复下单。
- **目标（target）**：通常是 URL（RFC 3986），标识要操作的资源，例如 `/api/users/42`。
- **首部（Headers）**：携带元数据，如 `Host`（指明目标主机，HTTP/1.1 起必需）、`User-Agent`、`Accept`（可接受的媒体类型）、`Content-Type`、`Authorization`。
- **主体（Body）**：可选，`POST`/`PUT`/`PATCH` 时放置要提交的数据。

### 响应与状态码

服务器返回一个**状态码**表明结果。三位数字按首位分五类，语义由 RFC 9110 统一定义：

- **1xx 信息**：如 `101 Switching Protocols`（协议升级，例如切到 WebSocket）；
- **2xx 成功**：`200 OK`、`201 Created`、`204 No Content`；
- **3xx 重定向**：`301` 永久迁移、`302` 临时跳转、`304` 未修改（命中缓存）；
- **4xx 客户端错误**：`400` 请求有误、`401` 未认证、`403` 禁止、`404` 未找到、`429` 请求过多；
- **5xx 服务端错误**：`500` 内部错误、`502` 网关错误、`503` 不可用。

响应首部如 `Content-Type`（主体的媒体类型）、`Content-Length`（主体长度）、`Cache-Control`（缓存策略）描述主体的格式与处理方式。首部还承担**内容协商**：客户端用 `Accept`/`Accept-Encoding`/`Accept-Language` 表达偏好，服务器据此返回合适的表示形式。

### 无状态与首部

HTTP 被设计为**无状态**：每个请求相互独立，服务器默认不记得上一个请求是谁。这带来极大的可伸缩性——任何一台服务器都能处理任何请求，负载均衡无需把用户「粘」在同一个后端。代价是「记住用户」需要额外机制：状态被显式地放在首部（如 `Cookie`）或后端存储中，而非协议本身。HTTP/1.1 的持久连接只复用 TCP 连接、并不共享应用状态，这一点常被混淆。

### 一次请求的完整旅程

把四个部分串起来看：用户在地址栏输入网址，浏览器先解析域名得到 IP，建立连接后把「方法 + 目标 + 首部（含可选主体）」组装成请求发出；路径上的代理与 CDN 可能代为应答；服务器（或其应用）依据方法与首部决定如何处理，返回状态码与主体；浏览器再根据 `Content-Type` 决定渲染还是下载，根据 `Cache-Control` 决定是否缓存。整条链路上，每一环都只依据报文里显式写明的信息行事——这正是无状态设计带来的可预测性：**任何一环都可以被替换，只要它说同样的语言。**

### 首部的类别与可扩展性

按作用，HTTP 首部大致可分为几类：表示元数据（`Content-Type`、`Content-Encoding`）、内容协商（`Accept`、`Accept-Language`）、认证（`Authorization`、`WWW-Authenticate`）、缓存（`Cache-Control`、`ETag`）、连接管理（`Connection`、`Keep-Alive`）、路由与来源（`Host`、`Via`、`Forwarded`），以及安全相关（`Strict-Transport-Security`、`Content-Security-Policy`）。它们构成 HTTP 的**可扩展面**——协议几乎不再新增方法或状态码，新能力大多通过新的首部字段加入，而旧客户端会按规则忽略自己不认识的字段。

### 一个例子：从点击到呈现

以打开一张网页为例。浏览器发出 `GET /index.html HTTP/1.1`，带上 `Host`、`User-Agent` 与 `Accept`；服务器返回 `200 OK`，首部里有 `Content-Type: text/html; charset=utf-8` 与 `Cache-Control: max-age=300`，主体是 HTML。浏览器解析 HTML 之后，会为其中每一个样式表、脚本与图片再发若干请求——这些请求彼此独立、互不知情，服务器不需要记得「上一次的用户是谁」。若某张图片已被缓存且尚未过期，浏览器甚至不会发出请求，而是直接从本地取用。整个过程清晰、可缓存、可代理，正因为每一步都被报文显式描述。

### 为什么这套设计容易被实现

HTTP 的报文几乎不用专门的库就能读懂：请求行与首部行是「字段名加值」的文本，用任何语言按行解析即可；这也让调试极其方便，用文本工具就能看到收发的内容。这种低门槛带来一个常被低估的后果：**任何人都能实现一个最小的客户端或服务器**，于是工具、代理、抓取器、测试框架、边缘函数大量涌现，生态的扩张速度远快于任何需要专门硬件的协议。简单不只是美学，它本身就是网络效应。

### 幂等性为什么重要

方法被划分为**安全**（不改变服务器状态，如 `GET`、`HEAD`、`OPTIONS`）与**幂等**（重复执行的效果等同于执行一次，如 `GET`、`PUT`、`DELETE`）。这套区分不是学究分类，而是网络现实的要求：请求可能超时、可能被重试、可能被缓存或代理重放。若一个方法既不安全也不幂等（如 `POST`），客户端就无法在超时后放心重发；这也解释了为什么支付类接口常要求客户端生成幂等键，把「不幂等」的操作在应用层补成幂等。

> 📝 编者注：正因为「无状态 + 文本可读的首部」，HTTP 才如此容易被调试、被代理、被缓存、被脚本化。简单，是它战胜更复杂协议的根本原因——而所有后来者为它补上的复杂性（状态、压缩、多路复用），都小心翼翼地维持在这层简单语义之上。
