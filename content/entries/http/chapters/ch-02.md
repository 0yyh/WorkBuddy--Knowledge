## 从 HTTP/1.1 到 HTTP/3 的演进

HTTP 的「语义」三十年来基本不变，变的是「如何在网络上传输这些语义」——**版本只是传输映射**。理解这一点，就能理解为什么 RFC 9110 的方法与状态码在三个版本里完全通用。

### HTTP/1.1：文本与持久连接

**HTTP/1.1**（RFC 9112，前身是 1997 年的 RFC 2068 与 1999 年的 RFC 2616）用纯文本报文，可读易调试：请求行、首部行、空行、主体，一目了然。它引入**持久连接**（默认复用一条 TCP 连接顺序发送多个请求），免去每次请求都重新三次握手的开销，是相对 HTTP/1.0 最重要的改进。但它有个老问题：同一条连接上的请求必须串行等待响应，前一个响应未完成，后面的请求即使已发出也无法提前返回——**应用层的队头阻塞**。实践中浏览器只能靠对同一域名开六条左右并行连接来缓解，代价是连接数膨胀与重复握手。

### HTTP/2：二进制帧与多路复用

**HTTP/2**（RFC 9113，2015 年 RFC 7540 的继任）做了彻底重构：把报文切成**二进制帧**，所有帧在一条 TCP 连接上按**流（stream）**标识多路复用，并行收发互不阻塞；用 **HPACK**（RFC 7541）压缩冗余首部，并把常用首部存入双方共享的动态表，只传索引；还支持服务器推送与流的优先级。语义完全不变，性能大幅提升。但底层仍跑在 TCP 上——**一旦 TCP 层丢包，所有流都要等它重传**，传输层的队头阻塞依旧存在。

### HTTP/3：搬到 QUIC 上

**HTTP/3**（RFC 9114）把传输层从 TCP 换成 **QUIC**（基于 UDP）。QUIC 在 UDP 之上自行实现可靠、有序与加密（内置 TLS 1.3），每条流独立确认与重传：某条流丢包不再拖垮其他流，**彻底解决传输层队头阻塞**。它还支持 0-RTT 快速恢复连接、连接迁移（换网络不断连，对移动设备尤其友好），并把握手与加密合并以减少往返。在丢包率高的移动与无线网络下，HTTP/3 明显更稳更快。客户端依靠 ALPN 协商与 HTTPS DNS 记录发现服务器是否支持 HTTP/3。

### 队头阻塞的三层含义

「队头阻塞」在 HTTP 语境里常被混用，其实至少有三层。第一层是**应用层**的：HTTP/1.1 一条连接上的请求必须排队，前者不快，后者就被挡住。第二层是 **TCP 层**的：TCP 保证按序交付，一旦某个段丢失，后续已到达的数据也要在内核缓冲区中等待重传，HTTP/2 的多路复用因此被 TCP 的这一个特性一起拖住。第三层关系到**首部压缩**：HTTP/2 的首部压缩依赖有序处理，若改成让每条流独立压缩，又会引入新的依赖风险。HTTP/3 用「每条流独立可靠」解决第二层，用新的压缩方案处理第三层，而第一层在它的地基上根本不存在。

### 建立连接的开销

版本差异还体现在建连成本上。HTTP/1.1 需要 TCP 三次握手（一个往返以上）再加 TLS 握手（TLS 1.2 需两个往返，TLS 1.3 一个）；HTTP/2 复用同一条连接，省去重复握手；HTTP/3 把传输与加密握手合并，首次连接一个往返，重连可用 0-RTT 直接携带应用数据——代价是 0-RTT 数据存在被重放的风险，因此只适合幂等请求。对高延迟网络（如跨洲访问）而言，**少一次往返往往比更高的带宽收益更明显**。

### 为什么要理解版本差异

对应用开发者而言，版本差异大多被库隐藏，但理解它们仍有实际价值。其一，**性能调优的着力点不同**：在 HTTP/1.1 上，减少请求数（合并资源、内联、雪碧图）收益显著；在 HTTP/2 与 HTTP/3 上，多路复用让「减少连接数」的策略失去意义，过度合并反而拖慢首屏，因为一个大响应会占用流的带宽。其二，**故障排查的层次不同**：流的重置、连接的迁移，都会在日志里呈现出与 HTTP/1.1 截然不同的现象。其三，**部署依赖基础设施**：启用 HTTP/3 需要负载均衡与 CDN 支持 UDP，而某些网络环境会屏蔽 UDP 流量，因此必须保留回退路径。**把版本当作可配置的传输选项，而不是需要开发者操心的语义差别，是更稳妥的心智模型。**

### 版本协商与回退

浏览器如何知道服务器支持哪个版本？答案在 TLS 握手里：客户端通过 **ALPN** 扩展列出自己支持的协议（如 `h2`、`http/1.1`），服务器从中挑选。HTTP/3 走 UDP，无法用同一条 TLS 连接协商，于是先通过 `Alt-Svc` 首部或 HTTPS 类型的 DNS 记录宣告「我也在 UDP 上提供 HTTP/3」，客户端下次再尝试。这种「先降级可用、再逐步升级」的策略，让新版本能在不破坏旧客户端的前提下部署。

值得一提的是，语义与版本解耦之后，中间设备（缓存、代理、防火墙）面对新版本时不必理解其传输细节，只需理解共享的语义层。这大大降低了升级的社会成本——**一种新传输方式能否成功，取决于它能否在尽量不惊动既有生态的前提下被采用。**

> 📝 编者注：2022 年的规范重写（RFC 9110 至 9114）把过去散落在各版本文档里的语义抽成一份与版本无关的规范，此后再谈「HTTP 是什么」不必先问「哪个版本」。**方法、状态码与首部是永恒的，版本只是把同样的请求/响应映射到不同传输的「方式」**。
