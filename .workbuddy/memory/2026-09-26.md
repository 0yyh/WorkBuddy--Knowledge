## R3 规模化压测（#426，已完成脚本 + 实测结论）
- 新增 `scripts/bench_scale.mjs`（@pks/core 级，不依赖浏览器）：载入真实已构建索引
  （apps/web/public/content/index：manifest/titleIndex/64 分片/postings 解码/65 df 桶），
  基线（≈318万字terms/2528 docs）vs 规模化 K=7（≈2229万字terms/17696 docs，贴近 2000 万字目标）。
- 实测（searchL2 单查询最优，52 查询 ×3 轮）：
  - 基线 p50 0.45ms / p95 2.08ms；K=7 p50 1.69ms / p95 6.83ms（p95 放大 3.29×，最坏单查询 10.6ms）。
  - **结论：2000 万字下检索延迟 <10ms p95，完全可接受，非架构瓶颈。**
- 内存 caveat：脚本把全部分片解码驻留（基线堆 454MB / K=7 1272MB）；真实 app 经
  `SHARD_CACHE_CAPACITY=32` LRU 懒解码，仅约半数（≈227MB / ≈637MB）。Android 低端机需关注，但惰性+有界，非阻塞。
- 运行：`cd packages/cli && node ../../node_modules/.pnpm/tsx@4.23.13/node_modules/tsx/dist/cli.mjs ../../scripts/bench_scale.mjs`。

## T4 AppContext 拆分（#424，评估结论：暂缓）
- 现状：StationState 字段多，但 `value` 已 `useMemo` 在 [bundle,tracks,loading,error,reload]，
  消费者仅在装载/错误/轨道变化时重渲染，非逐帧。且 `searchFullText` 是无状态函数、检索跑 Web Worker、
  结果存 SearchPage 局部 state —— **搜索状态本就不在 Context 内**，doc 的 "SearchContext" 前提不成立。
- T4 评级本就是 P2「低」且「当前规模 OK」。R3 实测检索延迟 <10ms p95，Context 拆分对延迟无收益。
- 决策：**暂缓**。若未来出现明确重渲染热点再按「拆分 Index/Status 两 Context（零新增依赖）」落地，
  不引入 zustand（与「零 UI 框架/保持轻量」原则冲突）。
