### P1-2：entries 26 字母分片 → slug 哈希 64 桶
- `packages/core/src/index/builder.ts`：entries 改按 `shardOf(slug, 64)` 分桶，文件名两位补零 `00..3f`（原 `a..z`）。
- **顺手修掉一个潜伏 bug**：原代码先 `JSON.stringify(manifest)` 再赋 `manifest.entryShards`，导致落盘 manifest 的 `entryShards` 恒为 `[]`，loader 长期靠 `letterOf(titleIndex)` 首字母兜底。现改为先算分片再序列化 → 新产物 `entryShards` 非空（实测 62 个）。`letterOf` 兜底保留，供旧 `[]` 产物过渡。
- **新增孤儿清理**：改分桶方案后旧字母分片会残留（`writeIndexFiles` 只写不删），且会被「首字母兜底」误取到**过期**数据。在 `packages/cli/src/commands/build-index.ts` 写前 `rmSync(.index/entries)`（entries 每次全量重建、不参与增量复用，故安全；只清 entries 不动 .index 其它产物如词典索引）。实测清理掉 26 个残留，62 个 hex 分片与 manifest 一致。

### df 桶压缩
- 新增 `packages/core/src/util/compress.ts`：`compressJson/decompressJson`（fflate zlib + base64 文本载体，与 shard-codec 的 postings 同款，可穿过 contentCache/OTA 文本管线），已在 `packages/core/src/index.ts` barrel 导出。
- `builder.ts`：`bucket-NNN.json` 由 pretty JSON 改为 `compressJson({n,df})` 单行 base64。
- 消费端两处同步改解压 + 回落旧明文：`apps/web/src/lib/loader.ts` `fetchDfBucket`、`packages/cli/src/load-index.ts`。worker 不直读桶（主线程 `loadDfBuckets` 加载后经 `dfb` 投递），无需改。
- **实测大小澄清**：df 64 桶未压缩仅 **1.33MB**、压缩后 **1.06MB**（1.25x）。此前笔记里「48MB df.json」是 2000 万字目标规模下的推算，当前 143 万词规模下 df 本身很小——df 分片化的真实收益是**按需懒加载**（每次查询只取 1–3 个桶），压缩是随规模上升才更明显的锦上添花。
