## 存储方案评估（纯分析，无代码改动）+ 三项调整方案细化
用户问 JSON 文件存储随内容增长是否成瓶颈/隐患、是否是 AI 生成效率低的原因。实测数据（当日）：content/ 824 文件 8.27MB，115 词条 / 542 节 / 86.2 万字；.index/ 159 文件 4.66MB，16 个 search 分片各 ~150KB，**df.json 单体 2.1MB（BM25 IDF 全量加载，是 20M 字目标下最大单点，23x 后 ~48MB）**。结论：文件式存储（YAML/MD 源 + JSON 派生索引）适合静态离线站，不换 SQLite；真正的效率瓶颈在「逐条对话式生成」而非存储介质。建议定向修复：① df.json 分片化/并入分片 postings；② builder 增量构建（现全量 O(N) 重分词）；③ 靠批量生成管线提效。另警告构建并发无锁、相关引用靠 lint 兜底、3 处格式消费点须同步（已有认知，复确认）。

**三项调整细化（当晚向用户讲解，未实施）**：① df.json 按词条哈希分桶（每桶独立小文件，worker 只按查询词取所需桶，varint+zlib 沿用 shard-codec），全局 df 语义不变；② 增量构建 = 每词条 contentHash 存 `.index/build-state.json`（不随包分发）+ 稳定哈希分片保证未动分片可复用 + df 改为「分片级 df 片段合并」免全量重分词，保留全量重建开关兜底；③ 批量管线五阶段：工作单（taxonomy 缺口选题）→ 素材获取（dump 解析暂存 staging）→ 批量生成（约定内嵌提示，一次产出完整词条 YAML+MD）→ 自动校验回路（lint 报错回灌重试）→ 人工抽查批准后落盘 `content/entries/`，后续 build/index 链路零改动。素材用维基内容须在 sources 记 CC BY-SA。

## 两个顽固 bug 根修（commit `07472ce`，2026-09-11 中午）
- **① 裂隙（关进度信息后章节条/面板与导航栏之间露正文 30px）**：真根因是 **CSS 自定义属性在「声明元素处」完成 var() 替换后按计算值继承**——`--reader-nav-h` 原声明在 `:root`，statusbar-h=30px 被烤进继承值；`.reader-no-statusbar` 覆写 `--reader-statusbar-h:0` 只影响直接引用它的导航栏/信息条，消费 nav-h 的章节条/`.reader-sheet`/子层 inset/`.reader-scroll` padding 全都不重算 → 上层不下沉、导航栏下沉，裂出一条缝。前两轮（挂类到 .reader-root / body）都只修了「直接引用」路径故不彻底。**修法**：`--reader-nav-h` 改为在 `.reader-root, body` 上计算（`:root` 只留两个高度基量）。此教训通用：**凡子作用域要覆写变量参与 calc 的，calc 必须放同一作用域声明**。
- **② 切章后点中央唤起失灵**：`[index]` effect 先 `scrollTo(0)` 后 `setChromeDismissed(false)`，但 scroll 事件异步晚到 → `hideChrome()` 见 overlay=true 把 chrome 重新滚隐 1.8s → 切章后「overlay 在而卡片不可见」，第 1 点把不可见 overlay 关掉、第 2 点打开时可能仍 dismissed → 需多次点击。修法三件套：`chromeSuppressRef` 抑制旗标（`[index]` effect 置位、hideChrome 消费、新章 load `.then` 复位——防旧内容已在顶部时 scrollTo 不发 scroll 事件导致旗标滞留）；`[index]` effect 补清 chromeRevealTimer；`onSurfaceClick` 唤起 overlay 时强制清 timer + `setChromeDismissed(false)`（保证首次点击必可见）。
- **验证**：临时 CDP 行为探针（用后已删）量化断言全过：关进度信息后章节条↔导航栏 gap=0px、设置面板↔导航栏 gap=0px、body 有 reader-no-statusbar；overlay 唤出态点「下一章」切章后 dismissed=false 且章节条 opacity=1；从关闭态点中央 1 次即唤起（dismissed=false、opacity=1）。typecheck EXIT 0、build 成功、e2e-reader-refactor ok:true、e2e-search-worker ok:true。实拍截图确认无裂隙。
