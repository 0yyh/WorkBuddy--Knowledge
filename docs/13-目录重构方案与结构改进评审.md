### 1.2 依赖链接形态（关键，影响所有"动 package.json"的建议）

```
D:\WorkBuddy--Knowledge\
├─ node_modules\                 ← 只有 2 项：.pnpm/(201 项 pnpm 布局) + @pks/
│  └─ @pks\core -> /d/WorkBuddy--Knowledge/packages/core     ← 手工 symlink
├─ apps\web\node_modules\        ← 83 项，全部是指向 node_modules/.pnpm/* 的 symlink
│  └─ @pks\core -> /d/WorkBuddy--Knowledge/packages/core     ← 手工 symlink
└─ packages\core\node_modules\   ← 独立 npm 安装的树（fflate / js-yaml / unified / … 11 项）
```

**实测推论（重要）：**

1. 最初的依赖安装**确实是用 pnpm 做的**（`node_modules/.pnpm` 存在且有 201 项），之后 pnpm 在此环境不可用，才补了两条手工 symlink。
2. **`fflate` 只存在于 `packages/core/node_modules/fflate`，不在根 `node_modules`，也不在 `apps/web/node_modules`。**
   → 从 `apps/web/src` 直接 `import { unzipSync } from 'fflate'` **会解析失败**（Node/Vite 从 `apps/web/src` 向上查找只经过 `apps/web/node_modules` → `apps/node_modules` → 根 `node_modules`）。
   → 但从 `@pks/core` 内部 import 可以解析（从 `packages/core/dist/...` 向上能找到 `packages/core/node_modules/fflate`）。**这一条直接决定了建议 2b 的实现路径。**
3. `@pks/core` 的 `"workspace:*"` 在 npm 下无法解析，全靠 symlink 兜着；一旦跑 `npm install`，`apps/web/node_modules/@pks/core` 大概率被重建为真实目录或从 registry 拉取失败 → **断链**。

### 2.5 诊断小结

按严重度排序的「真正值得动」的问题：

1. **R-4 / R-5（High）**：分片 LRU 未接线 → 30–50MB 常驻内存。**这是全项目性价比最高的修复点**，且 `PartitionLoader` 代码已写好，只差接线。
2. **R-1（High）**：`update.ts` 孤儿模块 —— 误判之源，且删除零风险（0 引用）。
3. **C-3（High）**：`.gitignore` 吞掉 Android 工程 —— 与 git init 强冲突，必须先修。

### 7.1 🔒 pnpm 三件套（`packageManager` / `pnpm-lock.yaml` / `pnpm-workspace.yaml`）

1. `apps/web/node_modules` 的 83 个包**全部是指向 `node_modules/.pnpm/*` 的 symlink**。这个目录结构是 pnpm 布局的证据。删除 `pnpm-lock.yaml` 不会立刻断链（文件只是声明），但**会让"恢复安装"这件事彻底失去依据**——本机 pnpm 不可用，npm 又不认识 `workspace:*`。

## 1a. 列表与目录是否需要虚拟滚动

### 判定：❌ **不采纳**（优先级 P3）

### 收益

**当前规模下收益为负。** 实测数据：

| 场景 | 最大条目数 | 实测来源 |
|---|---|---|
| 全站词条总数 | **101** | `content/entries` |
| 单个类目下最大词条数 | **≤ 101**（且实际被 6 大 L1 分散，L1 下还有 L2/L3） | taxonomy 179 行、101 词条 |
| 单词条章节目录（阅读页目录面板） | **9**（1 导读 + 最多 8 章，`das-kapital`） | 实测 max=8 |
| 阅读历史 | **200**（`MAX_ITEMS`，`history.ts:13`） | 代码常量 |
| 搜索结果（L1 标题匹配） | ≤ 101 | 同上 |

101 个 `<li>` 的 DOM 节点数约 500–800，浏览器首屏渲染 **< 16ms**。虚拟滚动的收益门槛通常在 **1,000+ 条**（此时 DOM 节点 > 5,000，滚动帧开始掉）。

### 成本

| 项 | 说明 |
|---|---|
| 引入依赖 | 若用 `@tanstack/react-virtual` / `react-window` → **新增依赖，违反项目硬约束** |
| 自研 | 需处理不定高 item（`BrowsePage` 的 `.card` 高度随 `clamp-3` 摘要行数变化）、滚动容器、键盘可达性、a11y → 约 200–400 行 |
| 维护 | 阅读页目录面板是**底部 sheet**（`reader-chapter-sheet`），其滚动容器与页面滚动容器不同，自研虚拟滚动要单独适配 |

### 风险（**这是决定性因素**）

虚拟滚动**只渲染视口内 DOM**，会直接破坏三件事：

1. **划词查词典不可用** —— `ReaderSelectionMenu` 依赖选区跨越真实 DOM 节点；虚拟列表下不可见区域的文本不在 DOM 里，长文跨段划词会截断。
2. **页面内查找（Ctrl+F / WebView find-in-page）不可用** —— 浏览器只能搜到已渲染节点。**移动端没有 Ctrl+F，但用户会期望"能搜到"**。
3. **锚点跳转 / 滚动位置恢复失效** —— 阅读页的 `pendingScroll`（`EntryReaderPage.tsx:134-157`，点击二级小节滚动到 `.prose h2/h3/h4`）依赖目标节点真实存在。

> `docs/05:97` 早已就此裁决：「**不用虚拟滚动（保护 Ctrl+F / 选区 / 锚点）**」。本次评估**维持原裁决**。

### 不适用之处

- 列表页（Browse/Home/Search）不是长列表场景，用户是**浏览**而非**滚到底**。
- 阅读页目录面板最多 9 项，虚拟滚动纯属自扰。
- 唯一可能接近门槛的是**阅读历史 200 条**（`HistoryPage`），但 200 条仍在安全区。

### 推荐技术选型

**不引入任何库。** 若未来历史页变长，优先用**零依赖的分页/增量渲染**（"加载更多"或 `IntersectionObserver` 触底追加），它不破坏 Ctrl+F（已渲染节点仍在 DOM）。

### 触发阈值（什么时候该重做这个决策）

| 指标 | 阈值 | 达到后做什么 |
|---|---|---|
| 单个列表最大条目数 | **> 800 条** | 先改「加载更多」增量渲染（零依赖） |
| 单个列表最大条目数 | **> 3,000 条** | 才考虑虚拟滚动，且**仅用于列表页，绝不用于阅读页正文/目录** |
| 首屏列表渲染耗时（真机中端 Android） | **> 200ms** | 先用 `content-visibility: auto` + `contain-intrinsic-size` 兜底（见 1b） |
| 滚动帧率（真机） | 列表滚动 **< 50fps** | 先查是否是 CSS `filter`/`box-shadow` 导致（本项目已踩过 `brightness` filter 的坑，见 `EntryReaderPage.tsx:521-528`） |

### 落地步骤

**无。** 但建议同步做两件零成本的事：
1. 给 `.card-list` / `.result-list` / `.toc-search-list` 加 `content-visibility: auto; contain-intrinsic-size: auto 120px;`（**零依赖、零风险、可随时回退**）。
2. 在 `docs/05:97` 的那行裁决旁补一句实测数据（"截至 2026-09-10，最大列表 101 条"），避免后人重复提问。

## 1b. 长文章：整篇加载 vs 分节懒加载

### 判定：⏸ **暂缓**（优先级 P2）

> 拆解：当前规模下**整篇加载完全够用 → 不做分节懒加载**；但**有两项零成本的 CSS/渲染优化应立即做**。

### 收益（当前 = 0；未来 = 高）

| 场景 | 实测 | 是否需要分节 |
|---|---|---|
| 最大单章 | **21,095 B ≈ 7,000 汉字**（`communist-manifesto/part-1.md`） | ❌ |
| 单章硬上限 | `SECTION_WORD_LIMIT = 20000` 字 | 由 `lint` 兜底（L008？需确认） |
| 实测渲染耗时 | 未测，但 7,000 字 Markdown → `renderMarkdown`（unified/remark/rehype + sanitize）在同量级内容上通常 **< 50ms** | ❌ |
| **未来 2000 万字档** | 若单章顶到 20,000 字上限，且出现超长章 | ✅ 需要 |

**注意**：`docs/05:97` 的设计目标是「长文首屏 ≤800ms、连续模式（>20k 字）不降帧」。当前最大章 7k 字，**距离该阈值还有 3 倍余量**。

### 成本

| 方案 | 成本 |
|---|---|
| **分节懒加载（chunk 化挂载，8k 字/块）** | **高**：需要把 `renderMarkdown` 的 HTML 输出切块 → 分块 `dangerouslySetInnerHTML` → 维护块级挂载/卸载 → 破坏 `pendingScroll` 锚点定位、破坏 `ReaderSelectionMenu` 的跨块选区、破坏 `chapterScrollPct`（`scrollHeight` 会随块挂载而变化，进度条跳变）。**在零测试（F8）的前提下，这是一次高风险重构** |
| **`content-visibility: auto`** | **极低**：纯 CSS，加在 `.prose` 的子元素上，浏览器自动跳过视口外渲染。**不移除 DOM**，因此 Ctrl+F / 划词 / 锚点全部保留 |

### 风险

| 方案 | 风险 |
|---|---|
| 分节懒加载 | 🔴 高：进度条计算失真（`scrollHeight` 动态变化）、二级小节跳转失败、跨块划词断裂、无测试网 |
| `content-visibility: auto` | 🟢 低：已知副作用是**滚动条高度会跳动**（需配 `contain-intrinsic-size`），以及**部分老 WebView 不支持**（Chromium 85+；`minSdk 23` 对应的系统 WebView 可能较老 → **需真机验证**） |

### 不适用之处

- 本项目**已经是"按章加载"了**（`docs[]` 数组切章，每章一次 `loadChapterDocument`）。用户说的"整篇加载"实际指的是**单章内**整篇渲染——而单章最大仅 7,000 字。**"分节懒加载"在架构上等于引入第三级粒度（词条 → 章 → 节），复杂度收益比不划算。**
- 阅读页已有 `autoLoad`（滚到章末自动加载下一章，`EntryReaderPage.tsx:306-319`），这已经是"纵向懒加载"的正确形态。

### 推荐技术选型

**当前（P2，立即做，零依赖）：**
```css
/* 只对长文段落块生效；保留 DOM → Ctrl+F / 划词 / 锚点不受影响 */
.prose > * {
  content-visibility: auto;
  contain-intrinsic-size: auto 200px;
}
/* 阅读页正文容器加 contain，隔离布局/绘制影响范围 */
.reader-scroll { contain: layout paint; }
```
> ⚠️ **必须真机验证**（`minSdk 23` / 国产 ROM WebView 版本参差）。建议：先加一个 `prefs` 开关或用 `@supports (content-visibility: auto)` 包一层，不支持时自动降级。

**未来（触发后才做）：** 分节懒加载按 `docs/05:97` 的原设计——「chunk 化挂载（8k 字/块）+ AST LRU(30)」，且**必须先把 `packages/core` 的 markdown 渲染结果做 AST 缓存**，而不是在 web 层切 HTML 字符串。

### 触发阈值

| 指标 | 阈值 | 达到后做什么 |
|---|---|---|
| 单章字数 P95 | **> 15,000 字**（逼近 `SECTION_WORD_LIMIT=20000`） | 做分节懒加载 |
| 单章渲染耗时（真机中端 Android） | **> 300ms**（可见白屏/卡顿） | 做分节懒加载 |
| 阅读页首屏可读时间 | **> 800ms**（违反 docs/05 指标） | 先做 `content-visibility`，再考虑分节 |
| 全站总字数 | **> 500 万字**（当前 44.3 万字，11 倍） | 重新评估整体渲染架构 |

### 落地步骤（当前，P2）

1. 在 `apps/web/src/styles.css` 加上述 CSS，用 `@supports` 包裹。
2. **真机验证**（至少一台 minSdk 23 附近的低端机或模拟器）：
   - 打开 `communist-manifesto/part-1.md`（最大章）
   - 验证：滚动 60fps、章末 `chapterScrollPct` 到 100%、点二级小节能跳到位、长按划词能跨段
3. 若任一项失败 → 立即回退（删 CSS 即可），转入 1b 的"未来方案"。

## 2a. 内置内容 + 远程更新相结合的模式

### 判定：✅ **建议采纳**（优先级 P1）

> 更准确地说：**这个模式已经落地了**（`content/` 随包 + IDB 覆盖层 + OTA），用户提的是"确认并加固"。需要补的是**打包格式**与**版本治理**。

### 现状核实

```
优先级链（已实现，lib/loader.ts:52-71）：
  isContentCacheActive()  ── true  → contentCache.getCached(relPath)  ── 命中即返回
        │                                    │ 未命中
        │ false                              ↓
        └────────────────→ fetch(public/content/*)  ← APK 内 assets/public/content（只读兜底）
```

- `content/` 随包（APK `assets/public/content`）✅
- 远程/局域网 OTA（清单 + 并发 6 + sha256 + 写 IDB + 激活）✅
- 本机文件导入（辅路，`importLocalFiles`）✅
- 清缓存回到随包内容（`resetContentCache`）✅

**缺口**：

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| G1 | **更新包是 642 个散文件 / 14.83 MB** | memory 2026-09-10:65 | 首更 642 个 HTTP 请求；`FETCH_CONCURRENCY=6` 下，单次 RTT 10ms 也要 ~1s 纯排队，真机 WiFi 上 RTT 常常 20–50ms → **几秒到十几秒**；且中途断网只能整批重来（虽有 sha256 但无断点续传） |
| G2 | **无版本回滚 / 无快照** | `applyContentUpdate` 直接 `putCached` 覆盖同路径 | 更新失败虽不激活（`failed > 0` 直接 return），但**部分文件已写入 IDB**，下次 `fetchText` 若 `active` 仍为 true 会读到新文件 → 潜在"半新半旧"（不过 `activated` 未置 true 时 `isContentCacheActive()` 为 false，实际安全 ✅） |
| G3 | **无增量** | 清单是全量 642 文件 | 每次更新都要全量比对（虽只下变化的，但**清单本身 + 642 次 HEAD/GET** 开销不小） |
| G4 | **无压缩** | `serve-lan.mjs` 直接托管明文 | 14.83 MB 明文传输（文本 gzip 后可压到 ~1/4，但 WebView fetch 走 HTTP 时服务端可开 gzip —— `serve-lan.mjs` **未开**） |

### 收益

| 项 | 收益 |
|---|---|
| 补 G1/G4（打包成单文件） | 642 请求 → **1 个请求**；14.83 MB → **约 3–5 MB**（文本内容 zip level 6）；支持 Range 断点续传 |
| 补 G2（版本快照） | 更新失败可一键回滚 |
| 补 G3（增量） | 小更新秒级完成 |

### 成本

| 项 | 成本 |
|---|---|
| 打包 | **低**：`createBundleZip()` **已经在 `@pks/core` 里写好了**（`merge/bundle.ts:30-54`，用 fflate `zipSync`）；`build-update.mjs` 里加一段调用即可 |
| 解包 | **低**：`extractBundleZip()`（`:83-90`）或 `zipVfsFromBytes()`（`vfs/zip.ts:10`）**都已在 `@pks/core` 主入口导出** |
| 客户端改造 | **中**：`contentUpdater.applyContentUpdate` 需分支支持 `format: 'zip'`；约 60–100 行 |
| **新增依赖** | **0**（走 `@pks/core` 包装，见 F1'） |

### 风险

| 项 | 风险 | 缓解 |
|---|---|---|
| zip 解压内存峰值 | 14.83 MB 明文解包 → 峰值内存约 40–60 MB（UTF-8 string + Uint8Array 双份） | ① 分包（按 `entries/<letter>` 分多个 zip）；② 用 `unzipSync` 后**逐文件释放**；③ 真机测内存 |
| 主线程阻塞 | `unzipSync` 是同步的，3–5 MB 解压约 100–300ms | 可接受；若不可接受，fflate 有 `AsyncZip` / Worker 版本（但会新增复杂度） |
| bundle 体积增加 | fflate 的 `unzipSync` 约 **+8–12 KB min** | 相对当前 JS bundle（约 420 KB）**+2~3%**，可接受 |
| 破坏现有散文件通道 | — | **保留双通道**：manifest 加 `format` 字段，旧通道 `files[]` 继续可用 |
| 无测试网（F8） | 中 | **`contentUpdater` 的纯函数（`isManifestShaped` / `normalizeManifest` / `relPathOfFile`）适合上移到 `@pks/core` 并补测试** —— 这也是 `项目结构整理与现状评估` §B.4 的既有建议 |

### 推荐技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 打包 | **fflate `zipSync`（level 6）**，经 `@pks/core` 的 `createBundleZip` | 已存在、零新增依赖 |
| 解包 | **fflate `unzipSync`**，经 `@pks/core` 的 `extractBundleZip` / `zipVfsFromBytes` | 同上；且 `zipVfsFromBytes` 返回 `Vfs`，与项目 VFS 抽象一致，未来可复用于"离线内容包" |
| 清单 | 扩展 `UpdateManifest`：`{ built_at, format: 'files' \| 'zip', files?: [], packs?: [{path, sha256, size, entries}] }` | 向后兼容 |
| 服务端 | `serve-lan.mjs` **增加 gzip**（`node:http` + `zlib`）—— 零依赖 | 即使不打包也能立刻省 3/4 流量 |
| 存储 | 继续用 `contentCache.ts` 的原生 IndexedDB | 不换 Dexie（见 2c-③） |

### 落地步骤（建议分两步，先做零风险的那步）

**Step 1（P1，零风险，立即做）**：
1. `scripts/serve-lan.mjs` 加 gzip 压缩（`node:zlib`，按 `Accept-Encoding` 判断，`.json`/`.md` 都压）。
   - 预期：14.83 MB → ~3.5 MB 传输，**客户端代码零改动**。
2. 修正 `contentUpdater.ts:8-9` 的过时注释（C-6）。

**Step 2（P1，需用户确认）**：
1. `build-update.mjs` 增加 `--zip` 模式：调用 `createBundleZip` 生成 `content.zip` + `manifest.json`（`format: 'zip'`）。
2. `contentUpdater.ts` 增加 `applyContentUpdateZip()`：`fetch(zip) → ArrayBuffer → extractBundleZip → 逐文件 putCached → setMeta`。
3. 保留 `applyContentUpdateFiles()` 旧路径，`format` 缺省为 `'files'`。
4. **真机验证**：14.83 MB → 单包；记录耗时与内存峰值（对比散文件方案）。

**Step 3（P2）**：版本快照 / 回滚：在 IDB 里存 `snapshot:<built_at>`，更新前把旧 `built_at` 记入 `meta`，失败时一键回滚。

| 测试 | 低–中 | 在 `packages/core` 加 1–2 个 round-trip 用例 + web 端手工验证 |
| **隐性成本** | **中** | 必须**通过 `@pks/core` 间接使用**（F1'：fflate 不在 web 的解析链上）。需确认 `@pks/core/dist` 里 `fflate` 的 import 能被 Vite 正确解析到 `packages/core/node_modules/fflate` |

> ⚠️ **F1' 的验证建议（执行前必做）**：
> ```bash
> # 在 apps/web 下临时建一个探针文件，import { zipVfsFromBytes } from '@pks/core'
> # 然后 npm run build，看是否报错 / 看 bundle 里是否出现 fflate 代码
> grep -c "fflate\|unzipSync" apps/web/dist/assets/index-*.js
> ```
> 若解析失败 → 备选方案：在 `packages/core/src` 新增一个 `zip.ts` 顶层封装（如 `export function unzipText(u8: Uint8Array): Record<string,string>`），从 core 内部 import fflate，然后**重建 dist**。仍是零新增依赖。

### 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 解压内存峰值（14.83 MB → 40–60 MB） | 🟡 中 | 分包（按首字母/类目切多个 zip，每个 ≤ 5 MB）；或先只压 `index/`（13.45 MB 里的大头是检索分片，压缩比最高） |
| `unzipSync` 主线程阻塞 100–300ms | 🟢 低 | 放在"检查到更新 → 用户点确认"之后，此时本来就有等待预期 |
| web 端零测试（F8） | 🟡 中 | 把解压逻辑**放在 `@pks/core`**（有测试基建），web 只做 IO |
| 破坏现有 OTA 通道 | 🟢 低 | 双通道并存，`format` 字段切换 |
| **"不可信 zip"安全** | 🟡 中 | `docs/05:143` 已确立「zip 视为不可信：导入前校验结构、限制文件类型、沙箱解析」。落地时需：① 校验 zip 内路径无 `..`、无绝对路径；② 限制解压后总字节数；③ 只接受 `entries/`、`index/`、`tracks/`、`dict/` 前缀（复用 `contentUpdater.ts:325` 的 `IMPORT_ACCEPT` 正则） |

### 不适用之处

- **APK 随包内容不建议 zip**。APK 本身已是 zip（压缩过的），再套一层 zip 收益≈0，反而增加启动解压开销。当前 `assets/public/content/` 散文件 + Android 自带的 assets 压缩是正确形态。
- **`content/dict/dictionary.json` 不建议单独压**。体积小，且它需要高频随机读取。

### 推荐技术选型

| 用途 | 选型 |
|---|---|
| 打包（构建期） | `fflate.zipSync(level 6)` via `@pks/core` `createBundleZip` |
| 解包（运行期） | `fflate.unzipSync` via `@pks/core` `extractBundleZip`（返回 `Record<path, text>`，**比 `zipVfsFromBytes` 更适合 OTA 场景**，因为要逐文件写 IDB） |
| VFS 场景（未来离线包） | `zipVfsFromBytes`（返回 `Vfs`，可与 `OverlayVfs` 组合） |
| 服务端传输压缩 | `node:zlib` gzip（`serve-lan.mjs`） |

## 2c. 用户数据存储选型：localStorage 是否够用 vs 引入 Dexie.js

> 用户把三个用途混在一句话里提了，但它们**结论完全不同**，必须分开评估。

### 2c-① 全文搜索索引 → 🟡 **部分采纳：先做 LRU（不动 Dexie）**（优先级 P1）

#### 现状核实（这是本节最重要的发现）

| 事实 | 证据 |
|---|---|
| 检索分片是**构建期产物** | `build:index` 生成 `index/search/title.json` + `index/search/sNN.json`（16 片） |
| 分片总大小 | **13.45 MB JSON / 17.6 万 term 键**（`loader.ts:130` 注释 + memory:128） |
| 设计的加载策略 | **LRU + IndexedDB 磁盘缓存**（`docs/02 §18.6`、`docs/05:128`） |
| 设计的实现 | `packages/core/src/index/lazy-loader.ts` 的 `PartitionLoader`（LRU capacity 12 + IDB 回写） |
| **实际的实现** | `apps/web/src/lib/loader.ts:92` `const shardCache = new Map<number, ShardIndex>()` —— **永不驱逐** |
| **实际的行为** | `warmSearchShards()`（`:133-144`）空闲时调用 `ensureAllShards(16)`（`:122-126`）把**全部 16 片拉进内存并常驻** |
| **`PartitionLoader` 使用情况** | **0 处**（`grep -rn "PartitionLoader" packages apps/web/src` 仅命中定义与 d.ts） |
| 常驻内存代价 | **+30–50 MB**（memory:128） |

**结论：真问题不是"用什么库存索引"，而是"设计好的 LRU 没接线，导致全量常驻内存"。换 Dexie 解决不了这个问题——因为代码压根没在往 IDB 里写分片。**

#### 收益

| 方案 | 收益 |
|---|---|
| **接线 `PartitionLoader`（推荐）** | 常驻内存 **30–50 MB → < 10 MB**；代码**已经写好**，只差接线 + 加固 |
| 引入 Dexie 存分片 | 同上，但需新增依赖 + 重写，**且 `PartitionLoader` 的 IDB 层已经能干这事** |

#### 成本

| 方案 | 成本 |
|---|---|
| 接线 `PartitionLoader` | **低**：① 把 `lazy-loader.ts:69-92` 的裸 IDB 封装对齐 `contentCache.ts` 的降级风格（~20 行）；② `loader.ts` 把 `shardCache: Map` 换成 `PartitionLoader`（~30 行）；③ `SearchEngine` 的 `shardLoader` 回调改造（当前是同步 `shardCache.get(shard) ?? null`，`PartitionLoader.load()` 是 async → **需要改 `SearchEngine` 接口或改为预加载后同步读**，这是唯一有技术难度的点） |
| 引入 Dexie | **高**：新增依赖（违反硬约束）+ 重写 `loader.ts` + 与现有 `pks-content-cache` DB 并存两个 DB |

#### 风险

| 方案 | 风险 |
|---|---|
| 接线 `PartitionLoader` | 🟡 中：`SearchEngine` 的 `shardLoader` 是**同步**签名（`loader.ts:177-179`），而 `PartitionLoader.load()` 是 async。改造路径：① 搜索前 `await ensureShards(needed)` 预加载所需分片（但 BM25 需要全部分片才能算全局 IDF…）；② 或改为"分片缺失时跳过 → 结果不精确"。**这是需要设计的点** |
| 引入 Dexie | 🔴 高：新增依赖 + 无测试网 |

#### 关键设计约束（必须提醒）

BM25 的 **IDF 依赖全库统计**。如果只加载部分分片，不同分片的 IDF 不一致 → 排序失真。因此：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | **把 IDF/全局统计抽出来单独一个小文件**（`index/search/stats.json`，含 `N`、每个 term 的 `df` 全局值），分片只存 `tf` + 局部信息。这样搜索时只需 `stats.json`（几十 KB）+ **命中分片** | 需改 `build-index` 产物格式 |
| B | 保持全量加载，但**改存 IDB 不存内存**（每次搜索从 IDB 读 16 片 → 慢） | 搜索变慢 |
| C | 分片只存 IDB，搜索时用 IDB 游标流式扫描（不整体读入内存） | 实现复杂，需 Worker |

> **建议先做 A 的调研**：`docs/02 §18.2` 里 `SHARD_COUNT` 16→64→256 的设计本就预设了"分片独立"。若现有 `sNN.json` 已含全局 `df`，则 A 可直接做；若含的是分片局部 `df`，则需改构建。

#### 推荐技术选型 / 落地步骤

1. **不引入 Dexie。**
2. `packages/core`：给 `lazy-loader.ts` 补健壮的 IDB 封装（复用 `contentCache.ts` 的那个思路，但 core 不能依赖 web → 在 core 内独立实现一份带降级的）+ 补 2 个 vitest 用例（LRU 驱逐、mock IDB 命中）。
3. 调研 `sNN.json` 的 `df` 是全局还是分片局部（读 `packages/core/src/index/builder.ts` / `inverted.ts`）。
4. 按调研结果决定：
   - 全局 `df` → 直接接线 LRU，按"命中分片"加载；
   - 分片局部 `df` → 先做 A（抽 `stats.json`），再接线。
5. 真机验证：首次搜索耗时（预热后 <50ms 的目标是否保持）+ Memory 快照（常驻 <10MB）。

#### 触发阈值（什么时候才该考虑 Dexie / IndexedDB 索引库）

| 指标 | 阈值 |
|---|---|
| 分片总大小 | **> 50 MB**（当前 13.45 MB） |
| 分片数 | **> 64**（`SHARD_COUNT` 从 16 升到 64 时必然要重做） |
| 首搜耗时（预热后） | **> 500ms** |
| 常驻内存 | **> 80 MB**（对 minSdk 23 设备已危险） |
| 全站字数 | **> 300 万字**（当前 44.3 万字） |

### 2c-② 阅读进度持久化（含当前文章与滚动位置）→ ❌ **不采纳 Dexie**（优先级 P3）

#### 现状核实

| 事实 | 证据 |
|---|---|
| 存储键 | `pks_lastRead`（`history.ts:106`）、`pks_readingHistory`（`:12`）、`pks_recentSearches`（`SearchPage.tsx:17`）、`pks_pref_*`（`preferences.ts:45-66`） |
| 数据结构 | `LastRead { slug, chapterIndex, updatedAt, scrollRatio? }` |
| **当前恢复了什么** | **只恢复了 `chapterIndex`** |
| `scrollRatio` | **字段存在但从未被写入**（`history.ts:103` 定义；`setLastRead()` 只做 `if (prev?.slug === slug && prev.scrollRatio !== undefined) rec.scrollRatio = prev.scrollRatio` —— 只透传旧值，**没有任何赋值点**） |
| 数据量 | 历史 200 条 × ~80 B = **~16 KB**；偏好 ~1 KB；合计 **< 20 KB** |

#### 收益

**引入 Dexie 收益 = 0。** localStorage 的容量上限通常是 **5–10 MB**，当前用量 **< 20 KB**，占用率 **< 0.4%**。即使未来内容涨到 2000 万字，阅读历史仍是 200 条上限（硬编码 `MAX_ITEMS`），数据量不变。

#### 真正该做的事（P2，低成本高收益）

**修 `scrollRatio` 从未写入的 bug：**

```ts
// history.ts —— 增加可选参数
export function setLastRead(slug: string, chapterIndex: number, scrollRatio?: number): void {
  // … 现有逻辑，若 scrollRatio 为有限数则写入
}

// EntryReaderPage.tsx:248-252 的 effect —— 目前只传了 slug + index
// 建议：在 scroll 的 compute() 里节流写入（复用已有的 rAF 节流）
// 或在切章 / 页面卸载（visibilitychange / beforeunload）时写一次
```

| 项 | 说明 |
|---|---|
| 成本 | 低（~20 行） |
| 风险 | 中 — **写入频率必须控制**：`chapterScrollPct` 每次 `onScroll` 都更新，若每次都 `JSON.stringify` + `localStorage.setItem`，会变成**同步 IO 刷屏**（localStorage 是同步 API，主线程阻塞）。<br>**推荐**：① 只在切章时写一次；② 加 `pagehide`/`visibilitychange` 兜底；③ 或 rAF 节流 + 500ms 去抖 |
| 不适用 | 不需要 IndexedDB。localStorage 够用 |

#### 触发阈值（什么时候该换 IndexedDB / Dexie）

| 指标 | 阈值 |
|---|---|
| localStorage 占用 | **> 2 MB**（当前 < 20 KB，100 倍余量） |
| 需要存的数据 | **阅读笔记 / 批注 / 高亮**（每条几百字 × 几千条）出现时 |
| 需要跨标签页/多端同步 | 出现时（但本项目是单端离线） |
| 需要事务性写入 | 出现时 |

> **提醒**：`docs/项目结构` 与 `PROJECT_STATUS` 都提到「笔记 / 评论 / 书签真实化（现为占位）」。**如果未来要做笔记/批注，那才是 IndexedDB/Dexie 的真正触发点** —— 届时可一并迁移，不建议现在为假想需求提前引入。

### 2c-③ 远程内容离线缓存 → ❌ **不采纳 Dexie**（优先级 P3）

#### 现状核实

| 事实 | 证据 |
|---|---|
| 已用 IndexedDB | ✅ `contentCache.ts`：DB `pks-content-cache` v1，store `files` / `meta` |
| 降级处理 | ✅ `idbFactory()` 探测（`:27-34`）；`open()` 5s 超时兜底（`:89`）；`onblocked` → null（`:86`）；**所有方法都不抛错** |
| 覆盖的用途 | ① OTA 下载内容；② 本机文件导入；③ 随包内容读回写（缓存优先） |
| 元数据 | `ACTIVATED_KEY` / `BUILT_AT_KEY`（`meta` store） |
| 清理 | `clearCache()` / `deleteCached()` / `listCachedPaths()` |

**这个功能已经完整落地并经过真机验证。** Dexie 能提供的增量：

| Dexie 能力 | 本项目是否需要 |
|---|---|
| Promise 化 API | ❌ 已有（`requestDone` / `requestValue`） |
| 事务封装 | ❌ 现有用法都是单 store 单操作，不需要跨 store 事务 |
| 索引 / 复合查询 | ❌ 只按主键（相对路径）get/put |
| 版本迁移 | ❌ 只有 v1，且永不迁移（缓存可随时清空重建） |
| 体积 | ❌ **Dexie min+gzip ≈ 25 KB**，相对当前 420 KB 的 JS bundle 是 +6% |
| 可观测性 | ❌ 不需要 |

**结论：换 Dexie 是净损失（+25 KB、+1 个依赖、+1 次无测试网的重构），换取的是语法糖。**

#### 唯一值得考虑的小改进（P3，可选）

`packages/core/src/index/lazy-loader.ts:69-92` 的第二套裸 IDB 封装**应统一**：
- 要么删除 `PartitionLoader` 里的私有 IDB 代码，改为接受外部注入的 `readIDB/writeIDB`（由 web 侧传入基于 `contentCache` 的实现）——**这是更干净的做法**；
- 要么把它对齐 `contentCache.ts` 的降级风格（当前它**没有超时兜底、没有 blocked 处理**，在隐私模式下可能挂起）。

**推荐前者的变体**：把 `PartitionLoader` 的构造签名改为接受可选 `persist?: { read, write }`，core 保持零 IDB 依赖（符合"主入口同构、不依赖 DOM/浏览器 API"的设计原则——**当前 `lazy-loader.ts:19` 的 `typeof indexedDB !== 'undefined'` 其实已经违反了这个原则**）。

> ⚠️ 这一点值得单独记一笔：**`packages/core/src/index/lazy-loader.ts` 在 core 主入口里直接用了 `indexedDB` 全局**，而 core 的设计约定是「主入口不依赖 DOM / 浏览器 API」（`packages/core/package.json:6` 描述）。这是一个**架构一致性问题**，虽然当前无功能影响（该模块 0 引用）。
