# PKS 项目全面评估（2026-09-12）

> 范围：代码架构 · 可维护性 · 性能效率 · 安全性 · 可读性
> 方法：静态代码审查（直接核对源码 / 配置 / 构建脚本）+ 跨维度风险归并。
> 基线：当前工作树干净，reader 修复已提交 `35f257d / cfb8de5 / 6432122` 并推到 gitee。

## 一、总体结论

PKS 是一个**架构目标清晰、安全性基线到位、动画/UX 已打磨到位的本地知识站**；短板集中在**工程化韧性（依赖解析脆弱）、搜索内存模型（有死代码 + 无界缓存）、Web 端测试覆盖薄、以及少量重复/巨型文件**。

整体评价：**可作为个人/家庭长期项目的健康度 B+**——功能与体验已达标，但若要让"第二个人也能安全接手或重构"，需先补齐 P0 项。

| 维度 | 评级 | 一句话 |
|------|------|--------|
| 代码架构 | B | monorepo 边界清晰，但 `@pks/core` 靠手工 junction 兜底，存在单点断链风险 |
| 可维护性 | B- | TS strict、无 `@ts-ignore`、无 UI 框架泄漏、注释到位；但 `noUnusedLocals` 关、`EntryReaderPage` 近千行、有重复逻辑 |
| 性能效率 | B | 动画/阅读渲染已优化；搜索内存无界 + 几处 O(N) 热路径是主要瓶颈 |
| 安全性 | B+ | Markdown 强制 sanitize、OTA 逐文件 SHA-256 + 原子激活；明文 OTA 与未签名清单是已知可接受风险 |
| 可读性 | B | 命名/注释/纯 CSS token 体系良好；巨文件 + 散落魔法数字是主要扣分项 |

## 二、分维度分析

### 2.1 代码架构

**优势**
- `packages/core`（isomorphic，消费其 `dist`）/`packages/cli`/`apps/web` 分层合理，`web` 只通过 `@pks/core` 公共 API 取能力，未反向依赖 web 实现。
- 构建流水线顺序明确（`build:index → build:chardict → content:copy → vite build → cap sync → gradlew assembleDebug`），根 `package.json` 与各子包 `scripts` 一一对应。
- 内容投递边界清晰：构建期 `.index/` → 投递改名 `index/` → web 按 `index/` 读，规则只在边界转换，未污染核心逻辑。

**薄弱环节**
- **`@pks/core` junction 是唯一致命脆弱点**（High）。`apps/web/package.json:21` 与 `packages/cli/package.json` 声明 `"@pks/core": "workspace:*"`，但 npm 无法解析该协议，实际靠手工 junction（`apps/web/node_modules/@pks/core → packages/core`）硬撑。一旦误跑 `npm install`/`pnpm install`，junction 被重建即断链，且无 git 回滚（node_modules 被忽略）。docs/13 已建议的 `scripts/check-links.mjs` 自检脚本**至今未实现**。
- **混合包管理元数据不一致**：根 `package.json` 写 `"packageManager": "pnpm@9.15.9"`，但项目红线明确禁止 pnpm；同时存在 `pnpm-workspace.yaml` 与 `package-lock.json` 混用迹象，新接手者极易踩坑。
- **死代码 `PartitionLoader`**：`packages/core/src/index/lazy-loader.ts` 已定义 LRU + IndexedDB 分区加载器，但 grep 全仓 **0 处引用**——搜索链路从未接入它，导致下面 2.3 的内存问题。

### 2.2 可维护性

**优势**
- `apps/web/tsconfig.json:10` `strict: true` + `noImplicitOverride` + `noFallthroughCasesInSwitch` + `forceConsistentCasingInFileNames`——严格度到位。
- **应用源码零 `@ts-ignore`/`@ts-expect-error`**（仅在 `node_modules` 内发现），零 TODO/FIXME/HACK 标记（仅 styles.css 中 "XXX" 误匹配）。
- **纯 CSS 约定守得住**：全仓未引入 Tailwind / MUI / Antd / styled-components（grep 命中均为 `bootstrapRoute` 等子串误报），设计 token 集中在 `tokens.css`。

**薄弱环节**
- **`noUnusedLocals`/`noUnusedParameters` 均 `false`**（`tsconfig.json:13-14`）——为"诊断死代码"刻意关闭，但代价是潜在死代码无法被编译器发现，需靠人工/评审兜底。
- **`EntryReaderPage.tsx` 976 行**是明显拆分之选（阅读设置三层 sheet、TOC、导航栏、滚动进度、选区菜单全挤在一个文件）；`builder.ts`(462) / `loader.ts`(380) 偏大但尚可。
- **逻辑重复**：字数口径在 `builder.ts` 与 `EntryCoverPage.tsx` 各算一份（已用"UI 兜底必须等于 builder 派生值"约束，但属重复真相）；索引加载逻辑分散于 `web/lib/loader.ts`、`cli/src/load-index.ts`、`builder.ts` 三处，规则变更易漏改。
- **Web 端测试覆盖薄**：仅 `relativeTime.test.ts` / `sysPrefs.test.ts` / `preferences.test.ts` 三个单测文件；搜索、loader、核心 hook、组件均无单测，唯一集成测试是 `e2e-reader-refactor.mjs`（93 断言，仅覆盖阅读器重构）。**安全重构的底盘不足。**
- **文档漂移风险**：`docs/` 含大量评审/报告（docs/11~14、reports/*、archive/*），部分已归档；与代码的一致性靠人工维护，无自动化核对。

### 2.3 性能效率

**已优化（避免误判，确认达标）**
- 阅读器面板：单一 `transform` 过渡、无冲突 `@keyframes`；拖拽走 `requestAnimationFrame` + 直写 `el.style.transform`，非逐 `pointermove` setState；`will-change: transform` + `backface-visibility: hidden`；`backdrop-filter` 已全部移除；`overscroll-behavior: contain` 就位。
- 阅读区一次只挂载一个章节 DOM，非整篇。

**主要瓶颈（已逐项核对源码）**
1. **（High）搜索分片内存无界 + `PartitionLoader` 死代码**：worker 内 `decoded = new Map()`（`search.worker.ts:44`）与主线程 `shardCache`（`loader.ts:104`）、`shardTextCache`（`loader.ts:107`）均**永不淘汰**；首搜即把 256 个分片（20M 字倒排）全部解码驻留，估算常驻 +30–50MB，低端 Android 易 OOM；且主线程降级路径会突然解码全索引。
2. **（High）L1 标题搜索每次按键 O(N) 重分词**：`SearchBox.tsx:68` → `engine.searchL1` → `searchTitleIndex` 在循环内对每条标题+别名调用 `tokenize`（`inverted.ts:130`），随词条规模线性增长。
3. **（Medium）BM25 倒排查找是线性 `postings.find`**：`inverted.ts:111` 在 `候选项 × 词项 × 倒排长度` 三重循环内对有序 postings 逐条 `find`，应改二分或解码期建 `Map<docId,tf>`。
4. **（Medium）无路由级代码分割**：`App.tsx:8-16` 静态 import 全部 9 个页面，Reader/Search/Settings 全进首包。
5. **（Medium）阅读页每滚动帧整页重渲染 + TOC 重算**：`EntryReaderPage.tsx:349` `setChapterScrollPct` 每帧触发大组件 reconcile；TOC 的 `docs.map().filter()` IIFE（`:896-969`）每次 render 都执行且未 `useMemo`。
6. **（Medium）Markdown 每次打开主线程重渲染、无缓存**：`renderMarkdown`（`parse/markdown.ts:31`，unified + rehype-sanitize）每章打开重跑全管线，无 memo/LRU；`content-visibility:auto` 未启用。
7. **（Medium）Worker 经 `@pks/core` barrel 引入 markdown 链**：`search.worker.ts:18` 引 barrel，连带把 `parse/markdown` 拉进 worker 图（故需 `workerDocumentShim` 兜底 module-scope `document.createElement`）——worker chunk 膨胀且主/worker 可能重复打包 core。

### 2.4 安全性

**优势（确认到位）**
- **所有渲染的 Markdown 强制 sanitize**：`renderMarkdown`（`parse/markdown.ts:14-28`）使用 `rehype-sanitize` + `defaultSchema`，仅额外放行 `code/span/div` 的 `className`（用于代码高亮）；`style`、事件处理器、`javascript:` 等危险属性/协议均被默认 schema 拦截。配合 `EntryReaderPage.tsx:673` 的 `dangerouslySetInnerHTML`，XSS 面被有效收敛。
- **OTA 更新完整性 + 原子激活设计良好**（`contentUpdater.ts`）：逐文件 `sha256` 校验（`:277-282`）、默认并发 6、部分失败不激活（`:298-301`）、空清单拒绝（`:265-268`）、路径归一化（`:153`/`:331`）；`importLocalFiles` 限制前缀 `^(entries|index|tracks|dict)/`（`:325`），无路径遍历。
- 仓内未发现密钥/令牌/私钥。

**风险（均属"个人局域网场景下可接受"，但应记录）**
- **`allowMixedContent:true` + `usesCleartextTraffic:true`**（`capacitor.config.ts:18` / `AndroidManifest.xml:13`）：为 App（`https://localhost`）拉取局域网明文 `http://192.168.x.x` OTA 所必需，是代价最小的对症方案；爆炸半径仅限用户自配的更新源地址，非任意远程。若未来走出个人 LAN，应改用 `res/xml/network_security_config.xml` 收窄到私网段。
- **OTA 清单本身未签名/未认证**：SHA-256 只证明"文件与清单一致"，不证明"清单可信"。在用户主动输入可信 LAN 地址的个人场景可接受；一旦暴露到不可信网络，恶意源可整体替换内容。属 Low/Medium，文档已说明。
- **非安全上下文下跳过校验**：`sha256Available()` 为 false 时仅告警跳过（`:259-261`）。App 运行于 `localhost`（安全上下文），实际可用；但若以 `http://` 打开 web 版则会降级，需在文档明确"web 版须 localhost/https 才启用完整性校验"。

### 2.5 可读性

**优势**
- 注释目的明确（如 `contentUpdater.ts` 头部说明"为何不用 zip"、`markdown.ts` 说明 sanitize 来源）；命名一致（`loadStation`/`loadChapterDocument`/`fetchShardText` 等动词短语清晰）。
- 纯 CSS + design token 体系（`tokens.css` 收敛动画时长/缓动/配色），阅读器动画令牌已落地。

**薄弱环节**
- `EntryReaderPage.tsx` 近千行，单文件承载过多职责，阅读成本高。
- 散落魔法数字：状态栏高度 `30px`、章节行 `52px`、`--reader-nav-h` 参与 `calc` 等硬写在 TS/样式中（动画时长已 token 化，但其余未统一）。
- `workerDocumentShim.ts` 是"markdown 链有 module-scope `document.createElement`"的补偿性 shim——属架构气味，根本解法是把该副作用移出模块顶层（见 P1）。

## 四、按优先级排序的改进建议

### P0 — 立即做，低风险高收益
1. **加 `scripts/check-links.mjs` 自检 + README 红线**：校验 `apps/web/node_modules/@pks/core` 与 `packages/cli/node_modules/@pks/core` 为指向 `packages/core` 的链接；在 `README` 与 `prepare` 脚本显式写"禁止 npm/pnpm install"。直接消除风险 #1。
2. **接入 `PartitionLoader`（或自建有界 LRU，cap≈16）**：替换 worker 内 `decoded` Map、主线程 `shardCache`，并在 worker 解码后删除 `shardTextCache` 对应项。代码已存在，仅缺接线——是性能 ROI 最高的一项（内存 +30–50MB → 数 MB，并消除降级 OOM）。
3. **L1 标题索引预分词一次**：在 `loader.ts` `loadStation` 时为每个条目预存 `Set<token>`，按键时只遍历预分词数据，消除每次 `searchTitleIndex` 的 O(N) 重分词。

### P1 — 重要，建议下一迭代
4. **BM25 倒排查找改二分 / 解码期建 `Map<docId,tf>`**：消除 `inverted.ts:111` 线性 `find`。
5. **路由级 `React.lazy` + `<Suspense>` 代码分割**：Reader/Search/Settings 懒加载，首屏更快。
6. **阅读页滚动帧优化**：进度条/滑块用 ref 直写（同 `useSheetDrag` 模式），TOC `docs.map().filter()` 加 `useMemo`，避免每帧整页 reconcile。
7. **Markdown 渲染结果 LRU 缓存**（按 slug+章节），或构建期预渲染章节 HTML，消除主线程重复 unified 管线。
8. **抽 `@pks/core/search` 子路径**：worker 只引 search 符号；把 `parse/markdown.ts` 的 module-scope `document.createElement` 移出顶层，去掉 `workerDocumentShim` 兜底，缩小 worker chunk。

### P2 — 打磨，按需
9. **拆分 `EntryReaderPage.tsx`**：把设置三层 sheet、TOC、导航栏、滚动进度抽成子组件/hook（如 `useReaderScroll`、`ReaderToc`），单行文件控制在 ~400 行内。
10. **统一魔法数字**：状态栏高度/`52px`/配色散值收进 `tokens.css` 或 `constants.ts`。
11. **提升 Web 单测覆盖**：补 `loader.ts`、`searchWorkerClient`、核心 hook 单测；新增 `shard-codec` 往返 + BM25 评分回归测试（守住内存/正确性改动不回退）。
12. **OTA 可选清单签名 + `network_security_config` 收窄明文范围**（若计划走出个人 LAN）。
13. **文档治理**：核对 `docs/` 与代码一致性，将过期评审移入 `archive/` 并标注日期；在 `docs/02` 明确"UI = 纯 CSS，禁 Tailwind/MUI"已落地。

## 五、已验证的优势（避免误判为短板）

- 阅读器动画管线已符合"单一 transform 过渡 + rAF 拖拽 + will-change + 无 backdrop-filter"最佳实践。
- Markdown 渲染已强制 `rehype-sanitize`，XSS 面收敛到位。
- OTA 已落地"逐文件 SHA-256 + 原子激活 + 空清单拒绝 + 路径白名单"，完整性模型健全。
- TS `strict` 开启、应用源码无 `@ts-ignore`、无 UI 框架泄漏、无 TODO/FIXME 技术债标记。
- 字数口径已在 builder 层统一派生（含 container 卷排除），UI 层仅做兜底求和，全量校验 122 词条一致。
