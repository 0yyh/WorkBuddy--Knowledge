## 1. 维度一：架构设计

### 问题清单

| 编号 | 问题 | 严重度 | 证据 |
|---|---|---|---|
| A1 | **依赖解析脆弱**：`@pks/core` 靠 junction 解析而非 npm/pnpm workspace，且 `node_modules` 重装即断；`package.json` 无 `workspaces` 字段 | 高(P0) | 工作记忆铁律「禁 pnpm/npm install/prune」；root `workspaces: undefined` |
| A2 | **无 CI/CD**：所有 lint/typecheck/build/APK 验证全靠本机手工，回归无护栏 | 高(P1) | 无 `.github/`、无 `.gitee/`；提交信息全为本地手动 |
| A3 | **生成管线已落地但未生产验证**：`cli/src/gen/` 含 FileProvider（pilot）与 OpenAIProvider，但无针对真实 LLM 路径的测试，内容仍主要靠人工/代理写作 | 中(P1) | 无 `gen` 相关测试文件；设计文档 §5 待明确事项多数仍未闭环 |
| A4 | **单测与 `.index/` 键强耦合**：47 处断言直接字面断言 `.index/...` 键（如 `df.json`、`sNN.json`），重构索引结构易碎 | 中(P2) | `system_design.md` §4.2；df 分桶已通过新增 `meta.json` 解耦 df 部分，但 sNN 键仍被 bundle 测试盯死 |
| A5 | **OTA 仅防损坏不防伪造**：sha1（http 非安全上下文）+ sha256（https），无签名 | 中(P2) | `contentUpdater.ts` 校验逻辑；设计定位为「可信局域网」 |
| A6 | **M 阈值跳变仍触发全量**：`chooseShardCount` 在 300万/1000万词处 16→64→256，跳变时旧分片全部失效 | 低(P2) | `system_design.md` §0；增量构建在 M 变时强转全量 |

### 改进方案

- **A1（P0）→ 规范化包解析**：把 `packages/core` 改为标准 `pnpm`/`npm workspace` + `file:` 依赖，或至少在仓库 `README` 固化 junction 创建脚本与 `core:build` 前置步骤。预期收益：消除「重装即断」的机器锁定，新环境 10 分钟可跑通。**优先级最高**。
- **A2（P1）→ 引入最小化 CI**：在 Gitee 用 `.gitee/workflows/` 加一条「lint + core/cli/web typecheck + 单测」流水线（无需真机构建 APK）。预期收益：每次推送自动拦截回归，降低单点失误。
- **A3（P1）→ 生成管线生产化**：补 `gen` 的 dry-run 用例（用 FileProvider 跑通 run→promote 闭环并断言落盘结构），为 OpenAI 路径加 mock 测试；把 `work-order` 模板纳入贡献指南。预期收益：内容规模化从「手工写作」走向「半自动 + 人工抽查」。
- **A4（P2）→ 解耦单测与键名**：将 `.index/` 键断言改为「结构契约」断言（存在性 + schema），而非字面路径。预期收益：后续分片/桶重构不再惊动 47 个用例。
- **A5（P2）→ OTA 可选签名**：在 manifest 增加 `signature`（仓库持有私钥离线签名，端上内置公钥验签），默认关闭、可开关。预期收益：若 OTA 误暴露公网也不被篡改。
- **A6（P2）→ 平滑 M 跳变**：把 sNN 分片改为「双窗口」过渡（新旧 M 共存一期）或按内容量分级预分配。预期收益：规避 2000 万字临界点的全量重算抖动。

## 2. 维度二：技术栈选型

### 问题清单

| 编号 | 问题 | 严重度 | 证据 |
|---|---|---|---|
| T1 | **纯 CSS 零 UI 框架**：无组件库，UI 复杂度上升后维护成本线性增加 | 中(P2) | `vite.config` 无 UI 框架；全部手写样式 |
| T2 | **web 构建无 Service Worker**：声称「离线优先」，但浏览器端无 SW/PWA，离线仅限 APK 资产内置 | 高(P1) | `grep` 全 `apps/web/src` 无 `serviceWorker`/`Workbox` |
| T3 | **仅 Android 端**：Capacitor7 只打包 Android，无 iOS / 桌面分发 | 中(P2) | 仅 `android/` 模块；无 `ios/` |
| T4 | **状态管理用 React Context**：当前规模 OK，但 `AppContext` 已承载 taxonomy/slugMap/engine/tracks/计数等多职责，易膨胀 | 低(P2) | `AppContext.tsx` 接口 `StationState` 字段众多 |
| T5 | **客户端 BM25 检索无召回增强**：无拼写容错、无同义扩展（dict 仅 248 条） | 低(P2) | 检索依赖 `fullTextSearch` + df 桶 |

### 改进方案

- **T2（P1）→ 补 PWA/Service Worker**：用 Vite 插件（如 `vite-plugin-pwa`）把 `dist/` 预缓存，使桌面浏览器也真正离线。预期收益：「离线优先」名副其实，扩大可用场景。**或**在文档明确「离线=APK+OTA，web 为在线浏览」，消除歧义。
- **T1（P2）→ 引入轻量样式体系**：采用 CSS Modules 或极简原子类（如沿用纯 CSS 但加 design tokens + 组件级 scoped），不引入重型 UI 库以保持体积。预期收益：UI 改动提速、一致性提升。
- **T3（P2）→ 评估 iOS/桌面**：若目标用户有 iPhone/Mac，加 Capacitor iOS target（需 Mac 构建机）。预期收益：覆盖更广，但成本较高，按需求优先级排。
- **T4（P2）→ 拆分 Context / 引入选择器**：把 `StationState` 拆为 `IndexContext` + `SearchContext`，或接入 `zustand`（极轻）。预期收益：减少重渲染、职责清晰。
- **T5（P2）→ 检索召回增强**：复用 `dictionary.json` 做同义回查，对查询词做编辑距离模糊匹配。预期收益：长尾查询命中率提升。

> 正向：React18 + Vite5 + TS `strict:true`（已开）+ 同构 `@pks/core`（node:fs 隔离在 `/node`、`/build`）选型合理，应保持不变。

- **C5（P2）→ 抬高中位线**：把目标从「≥1200」调为「中位 1600–2400、下限 1300」，用 gen 管线或代理批次对临界带做二次扩写。预期收益：抗回退、阅读体验更扎实。
- **C6（P3）→ 互联检查**：在 lint 加一条「新词条 must 在 ≥N 个已有词条 see_also 中被引用」的软告警。预期收益：知识网络更密。

## 4. 维度四：工程化与构建 / 分发

### 问题清单

| 编号 | 问题 | 严重度 | 证据 |
|---|---|---|---|
| B1 | **APK 构建手工脆弱**：无 `@capacitor/cli`（不能 `cap sync`），需手工拷 `dist/**` 到 android assets；gradle 经 PowerShell 且硬编码 JDK19/Android SDK 路径，管道曾致假失败 | 高(P1) | 工作记忆 APK 流程；本次构建实测 |
| B2 | **无自动化签名/发布**：产物为 debug 签名 APK，无法上架应用商店 | 中(P2) | 仅 `assembleDebug` |
| B3 | **分发瓶颈**：OTA 限局域网，远程/离线用户只能手动 sideload APK | 中(P2) | `serve-lan.mjs` 局域网托管 |
| B4 | **构建脚本散落**：根目录 `scripts_*.mjs` 与 `scripts/` 并存，职责重叠 | 低(P3) | 仓库根多支脚本 |

### 改进方案

- **B1（P1）→ 固化一键构建**：把「build:index → vite build → 同步 assets → gradle」串成单条 `npm run apk` 脚本（保留 `*>` 重定向修正，固化 JDK/SDK 环境变量检测）。预期收益：构建从「多步易错」变「一键可复现」。
- **B2（P2）→ 上架准备**：配 `assembleRelease` + keystore 离线保管 + 自动对齐/签名；如需商店分发再做。预期收益：可对外发布。
- **B3（P2）→ 分发多样化**：除局域网 OTA 外，提供「导出整包 zip + 端内导入」或私有网盘镜像，解除 LAN 依赖。预期收益：远程用户也能更新内容。
- **B4（P3）→ 脚本归并**：把根 `scripts_*.mjs` 收口进 `scripts/`，统一 CLI 入口。预期收益：维护心智负担下降。

## 5. 维度五：测试与质量保障

### 问题清单

| 编号 | 问题 | 严重度 | 证据 |
|---|---|---|---|
| Q1 | **缺端到端/集成测试**：OTA 更新流、生成管线闭环、APK 冒烟均无自动化 | 中(P1) | 仅 core/web 单测 |
| Q2 | **生成管线无真实路径测试** | 中(P2) | 见 A3 |
| Q3 | **单测脆性**：断言 `.index/` 字面键 | 中(P2) | 见 A4 |
| Q4 | **web 测试 95 例但可能未覆盖 OTA/检索降级路径** | 低(P2) | 需核对 `apps/web/src` 测试分布 |

### 改进方案

- **Q1（P1）→ 加三类集成测试**：① OTA 模拟「manifest+损坏文件→回退」；② gen `run→promote` 用 FileProvider 跑通；③ APK 用 `apkanalyzer` 或解包断言 `assets/public/content` 存在。预期收益：三大高风险路径有回归护栏。
- **Q2（P2）→ mock LLM 测试**：对 OpenAIProvider 做 `fetch` mock，断言解析/重试/限流。预期收益：provider 故障可定位。
- **Q3（P2）→ 解耦键名断言**（同 A4）。
- **Q4（P2）→ 补检索降级用例**：worker 不可用走主线程 `fullTextSearch` 兜底路径的测试。预期收益：弱网/老设备不崩。

## 8. 一句话总结

PKS 在**内容质量、索引/检索架构、三大性能优化**上已相当成熟；最该优先补的是**工程可复现性（包解析 + 一键构建 + CI）**与**离线形态一致性（web PWA）**，其次是**内容域均衡**与**单点运维去风险**。上述 P0/P1 落地后，项目可从「个人精修站」稳妥迈向「可协作、可规模化、可分发」的知识产品。
