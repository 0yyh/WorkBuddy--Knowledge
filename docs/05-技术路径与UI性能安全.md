## 0. 技术骨架复盘：能不能胜任？

**结论：架构成立，但必须补三块纪律，否则会翻车。**

原骨架（02）：React+Vite+TS 一套代码 → Capacitor 打包；无数据库（正文文件 + 分片索引入 Worker）；自研 CJK 倒排 + BM25；长文 chunk 化挂载。**方向正确**，但原文档对三件事着墨不足，而这三者直接决定你的两个硬指标（安全、秒开+流畅）：

| 补强 | 为什么必须加 | 否则 |
|------|--------------|------|
| **S1 渲染层强制 sanitize** | 内容含 AI 生成 + 用户导入，皆不可信 | Markdown 里的脚本被执行 = 存储型 XSS，破坏"手机安全"承诺 |
| **S2 明确性能预算与可测指标** | "秒开""丝滑"是主观词，必须量化 | 没有 FCP/TTI/FPS 目标，验收时无从判断 |
| **S3 UI 库减重** | 默认栈里的 MUI 偏重 | 拖慢秒开、增大包体 |

## 1. 技术选型（最终建议，修订默认栈）

| 层 | 选型 | 说明 |
|----|------|------|
| 框架 | React 18 + Vite + TypeScript | 一套代码，Web 直跑 + Capacitor 打包（沿用） |
| **UI 组件** | **Tailwind + 少量 headless 组件（Radix / shadcn）** | **不再用 MUI**（MUI 包体大、运行时重，拖累秒开）；阅读类 App 组件少，headless + 自写样式更可控更轻 |
| 状态 | **Zustand**（轻量） | 关键：**滚动位置 / 阅读进度不进 React state**，避免滚动触发整页重渲染（见 §3） |
| Markdown 渲染 | **react-markdown + rehype-sanitize（+ remark-gfm / remark-math）** | 渲染与 sanitize 一体；公式、表格、GFM 原生支持；「编者注」用自定义组件渲染 |
| 存储 | 沿用 02：无 DB；正文 VFS overlay + 分片索引入 Worker | — |
| 搜索 | 沿用 02：自研 CJK bigram 倒排 + BM25，16 分片 | — |
| 打包 | Capacitor 7（Android 先行） | — |
| 动画 | **仅 CSS transform / opacity（GPU 合成）**；必要时 Framer Motion（仅页面转场，非长列表） | 禁用 width/height/top/left 动画 |

> 与默认栈的差异：MUI → Tailwind+headless，是其一；是否保留状态库自选，Zustand 仅为推荐。

## 2. UI 整体布局

### 2.1 桌面 Web（三栏 + 顶栏）
```
┌───────────────────────────────────────────────┐
│ 顶栏：搜索框 · 主题切换 · 导入导出              │
├──────────┬────────────────────┬──────────────┤
│ 类目树   │   阅读区（正文）    │  TOC / 注解  │
│ + 学习路径│   （衬线、舒适行宽） │  滚动高亮    │
└──────────┴────────────────────┴──────────────┘
```
- 左栏：类目树 + 学习路径（Track）切换；可折叠。
- 中栏：正文阅读，行宽 65–75 字符、行高 1.7、衬线字体。
- 右栏：当前词条 TOC（页内锚点）+ 该条「编者注 / 溯源」侧栏。

### 2.2 手机 App（底部 Tab + 面包屑 + 沉浸阅读）
```
┌───────────────────────┐
│ 面包屑：政治理论 › 马克思主义 │  ← 两级下钻为主
├───────────────────────┤
│                       │
│      阅读区（沉浸）     │  ← 全屏、字号可调、夜间/护眼
│                       │
├────┬──────┬───────────┤
│类目│ 最近 │  我的     │  ← 底部 3 Tab
└────┴──────┴───────────┘
        ╭──╮  ← 搜索 FAB
```
- 无左侧栏：两级下钻 + 顶部面包屑为主导航；可搜索的全局类目抽屉为辅；章节用 Bottom Sheet。
- 阅读页全屏沉浸，滚动时底 Tab 自动隐藏。
- 搜索：右下浮动按钮（FAB）唤起。

### 2.3 阅读排版（两端共用规范）
- 衬线正文（系统宋体/Noto Serif 预加载，防 FOUT 抖动）；正文区最大宽度约束，避免长行。
- 三主题：亮 / 暗 / 护眼（sepia）；字号 ±调节。
- **「编者注」视觉隔离**：原文衬线正文 vs AI 导读/注释用灰底引用块 + 角标来源，一眼可分（正确性 + 呈现双关）。
- 内链 `[[...]]` 可点跳转 + 反链（"哪些词条链到我"）。

---

### 2.4 选区工具条（阅读辅助统一交互，2026-09-06 新增）

词典、高亮、复制、标记问题**共用一个选区手势**：移动端长按拖选 / 桌面端鼠标选区 → 浮现工具条。这是 R-20 / R-12 / R-17 / R-14 的统一入口，也是"零额外学习成本"的关键。

工具条四项：
- **查词**：本地离线词典（生僻字 / 成语 / 英文三套），弹卡显示释义，零网络。
- **高亮**：标记或取消高亮；可加小注。
- **复制**：复制 / 分享片段（自动带"出自《XXX》"引用格式）。
- **标记问题**：写 `feedback.json`（错 / 冗余 / 过简 / 缺项 / 存疑），进入 `04 §2.6` 闭环。

- 工具条为轻量浮层，不进 React 重渲染路径（延续 §3 原则）；出现 / 消失仅 `transform/opacity`。
- 查词数据与主索引同法分片、Worker 后台就绪，**不阻塞首屏、不影响秒开**。
- 与"滚动隐藏底栏"（§2.2）不冲突：选区时底栏本就非交互焦点。

## 3. 渲染流畅度（如何不卡）

| 手段 | 作用 |
|------|------|
| 长文 chunk 化挂载（8k 字/块）+ `content-visibility:auto` + AST LRU(30) | 沿用 02，避免整本解析；不用虚拟滚动（保护 Ctrl+F / 选区 / 锚点） |
| **滚动状态不进 React** | 用 IntersectionObserver + 原生/store 驱动 TOC 高亮，**绝不让滚动触发整页 re-render**——这是 React 阅读 App 卡顿的头号原因 |
| 动画只用 transform/opacity | GPU 合成，60fps；禁用 width/height/top/left 动画；`will-change` 谨慎（防合成层爆炸） |
| 字体预加载 | 避免长文首屏字体抖动（FOUT/FOIT） |
| 索引后台加载 | 首屏先渲染，搜索索引在 Worker 里异步就绪，不阻塞交互 |
| **量化指标** | 滚动 60fps；长文首屏 ≤800ms；TOC 高亮零卡顿；连续模式（>20k 字）不降帧 |

## 4. 秒开（instant open）策略

```
冷启 → 原生 splash（Android）保持在屏
  → WebView 预热/保活
  → 首屏 Shell（本地、零网络，立刻可交互）
  → 索引在 Worker 后台加载（L1 标题索引 0.3s 先就位兜底）
  → 全文索引 1.5–2.5s 后台就绪
```

- **代码分包**：Shell + 阅读器懒加载；搜索 / 索引 / 编辑 按需加载，初始 JS 控制 < 150–200KB（gzip）。
- **本地内容 = 启动零网络**，这是秒开的最大红利。
- **可测目标**：中端 Android 冷启 FCP ≤ 500ms、TTI ≤ 1s；首屏可读不依赖索引。
- Capacitor 可将 WebView 预创建/保活，进一步压低感知延迟。

> **⚠️ 2020 万字档修订（2026-09-07，决策 #11–#13）**：用户内容将达 2000 万字，**"L2 全文 1.5–2.5s 后台全量就绪"一行作废**。冷启动链改为（详见 02 §18.6）：
> ```
> splash → Shell(读 manifest+裁剪 taxonomy+L0/L1，≤300ms，UI 立即可交互)
>   → Worker 后台补 L1(≤300ms)
>   → 用户进入学科/词条 → 懒加载 entries 分区 + 该学科摘要分区(≤3s 后台)
>   → 首次全库正文检索 → 分区流式加载(LRU)，UI 显示进度(深检索低频可等待，决策 #12)
> ```
> 即"首屏与全文索引彻底解耦"——FCP≤500ms/TTI≤1s 仍成立。索引分区 16→256、Worker 内存分级常驻(L0/L1)+按需懒加载+LRU+IndexedDB 磁盘缓存、Worker≤128MB（不引 SQLite）；内容三层分发（Seed 随包≤45MB / 学科摘要包 / 学科全文包按需导）。P4/P8/P15/P16/P17/P18 目标见 02 §18.5。

## 5. 安全性（重点，用户强约束）

### 先给结论
- **操作系统沙箱已保证"一个 App 不会影响手机上其他 App"**：Android/iOS 每个应用独立沙箱，本地文件与内存相互隔离。你担心的"影响其他 App / 手机安全"在架构层被系统兜底——前提是**不滥用权限、不引入远程代码**。
- 真正需要防守的攻击面只有两处：**内容渲染** 与 **权限**，不是"沙箱逃逸"。

### 风险与对策

| # | 风险 | 对策 |
|---|------|------|
| 1 | **Markdown XSS（最关键）** | 渲染层**强制 sanitize**（rehype-sanitize / DOMPurify），禁止执行任意 HTML/JS；AI 生成与导入内容皆按不可信处理 |
| 2 | **导入包不可信** | zip 视为不可信：导入前校验结构、限制文件类型、沙箱解析、拒绝任何脚本执行；畸形数据走 Lint 拒绝 |
| 3 | **权限最小化** | 一期纯本地 + 手动导入 → **App 可申请"不联网"**（无 INTERNET 权限）→ 无网络 = 近零远程攻击面；同步等联网能力留二期按需开放 |
| 4 | **文件访问隔离** | 只用 Capacitor Filesystem 限定 App 私有目录，禁止 `file://` 越权遍历 |
| 5 | **依赖与插件** | 仅装必要 Capacitor 插件、保持更新；不引人不明来源的包 |
| 6 | **无远程代码** | 不加载远程脚本、不用 `eval`、不动态注入；所有 JS 打包进本地 |
| 7 | **密钥** | 一期 App 内无密钥（AI 录入在桌面 CLI，key 不进手机） |

> 一句话：**离线 + 无网络权限 + 渲染 sanitize + 沙箱**，是这套本地知识 App 最稳的安全底座。
